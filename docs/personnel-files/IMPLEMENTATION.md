# Фото и документы сотрудников

Файловый процесс с привязкой сертификатов к `employee_documents`. Остальные назначения файлов сохраняют самостоятельный процесс. Основан на [руководящем документе](https://chatgpt.com/space/page_aa3074a2cd9c8191b0698d4aae4321f6); связь с реестром и проверка соответствий добавлены по последующему поручению пользователя.

## Сертификаты и редакции классификатора

Миграция `pfiles002` добавляет nullable-связь версии файла с записью `employee_documents`, явную ссылку на заменяемую версию, централизованные редакции, специальности, подтверждённые направленные соответствия и журнал их ведения. Миграция не меняет существующие строки реестра, статусы, даты или старые файлы и не подставляет редакцию либо соответствие по названию или коду.

При загрузке можно выбрать существующий действующий сертификат реестра того же физлица, ещё не связанный с файлом, либо создать новую запись с реквизитами. В новой записи сохраняются специальность реестра, дата выдачи, срок действия, точное название специальности на выданном документе, код и редакция классификатора. PDF не переименовывается в реестровый документ и не распознаётся автоматически: кадровик проверяет соответствие скана реквизитам. Новая запись, созданная загрузкой, до одобрения имеет `DRAFT/UNVERIFIED`, после возврата `DRAFT/REJECTED`, после одобрения `ACTIVE/VERIFIED`. Привязка скана к старой записи с неизвестными сведениями не заполняет их автоматически и не меняет прежние статусы реестра.

Исходные название, код и редакция неизменяемы. Реквизиты связанной записи защищены от перезаписи; исправление производится новым документом. Реестр отображает сохранённое название, если оно известно, а не новое имя из текущего справочника. Старые записи с неизвестной редакцией не приобретают её автоматически. Архивирование записи реестра, связанной с файлом, через старый общий API запрещено: решение выполняется в файловом процессе.

При одобрении сервер блокирует физлицо и версии, заново читает реквизиты реестра и проверяет одно из оснований: та же запись специальности в той же редакции либо прямое активное центральное соответствие между разными редакциями, действующее на дату выдачи нового документа и на дату решения. Совпадение названий, должностей, кодов разных редакций, обратная или транзитивная цепочка не считаются соответствием. Неизвестные реквизиты блокируют замену. Сервер также проверяет токен сравнения, показанного кадровику; устаревшее сравнение нужно открыть заново.

При отказе HTTP 409 прежняя одобренная версия и её запись реестра сохраняются. При одобрении меняется только выбранный комплект и связанная прежняя запись (`SUPERSEDED`), без изменения исходного срока действия. Другие сертификаты физлица сохраняются. Отдельная подача создаёт отдельную запись и не требует соответствия прежним сертификатам. Отзыв файла снимает активность его связанной записи реестра, не переписывая реквизиты. Одобрение и замещение содержат в аудите сравнение и основание; заблокированная попытка — отдельное событие `replacement_blocked`.

Перед одобрением кадровик видит прежний и новый сертификаты, исходные названия, коды и редакции, даты и основание, а также кнопки просмотра обоих PDF. Основные решения остаются «Одобрить» и «Вернуть с пояснением». Открыть сравнение и подтвердить — два нажатия; просмотр и закрытие обоих PDF добавляют четыре нажатия. Соответствие не вводится в конкретной заявке.

Страница `/directory/personnel/certificate-classifiers` служит централизованному ведению редакций и соответствий. Изменения разрешены только уполномоченному сотруднику отдела кадров: одновременно требуются GLOBAL-разрешение `CERTIFICATE_CLASSIFIERS_MANAGE` и GLOBAL-кадровое полномочие `HR_ENROLLMENT_MANAGER` или `PERSONNEL_FILES_REVIEW`, без явного запрета. Технические администраторы и помощники не получают это право автоматически. Определение разрешения создаётся миграцией без назначения пользователям. Источник, пояснение, дата действия и подтвердивший кадровик обязательны; изменения журналируются. Отключение редакции для новых записей и отзыв соответствия не переписывают ранее выданные сертификаты.

## Пользовательский процесс

В личной и кадровой карточке появился раздел «Фото и документы». Работник подаёт фото лица, сертификат, диплом, удостоверение или основание изменения ФИО. Кадровик может подать файл от имени работника. Загруженная версия проходит антивирусную и техническую проверку, затем получает `pending`. В кадровой очереди `/directory/personnel/file-review` доступны одобрение и возврат с обязательным пояснением.

Одна версия содержит один исходный JPEG, PNG или PDF; многостраничный PDF рассматривается целиком. Несколько отдельных изображений следует объединить в один PDF до загрузки. Произвольные комплекты из нескольких файлов в одной версии пока не поддерживаются.

Одобренная версия доступна руководителям в их области. Новая версия не заменяет действующую до одобрения. Возврат не изменяет действующую версию. Отзыв закрывает публикацию. Архивирование сохраняет содержимое и историю; физического удаления нет. Возврат, одобрение, отзыв и изменение ФИО создают постоянные уведомления в разделе файлов самого работника; кнопка «Отметить прочитанным» сохраняет отметку на сервере. Внешние сообщения через Telegram или email не отправляются.

Файлы в карточке и защищённом просмотрщике выдаются через аутентифицированные запросы, PDF показывается как растровые страницы. Оригиналы доступны для скачивания только кадровикам и владельцам одобренных сертификатов/дипломов. Печать проверяет те же права. Запись о печати означает запрос страниц для печати, а не подтверждение физического отпечатка. Просмотр нельзя технически защитить от снимка экрана.

Изменение ФИО — отдельное подтверждение кадровика после одобрения основания и удостоверения личности. До подтверждения ФИО не меняется. Проверяется текущее ФИО, версия основания и дата действия; будущие даты не поддерживаются. Меняются поля `persons` и отображаемое ФИО связанных `employees`; запись с прежними и новыми значениями и идентификаторами оснований попадает в файловую историю и кадровый журнал. Идентификатор физлица сохраняется.

## Права

- Владелец разрешается по действующей связи `users → employees → persons`; неоднозначные связи закрываются.
- Непосредственный начальник определяется действующей административной связью `user_supervisors`; название должности не даёт доступа. Историческая схема без полей периода также поддерживается.
- `PERSONNEL_FILES_READ` предоставляет просмотр одобренного содержимого. Для директора назначается явное разрешение `GLOBAL`, для курирующего заместителя — `ORG_UNIT` с нужным `scope_id` и осознанным `include_subtree`. Автоматических назначений пользователям или платформенным ролям миграция не делает.
- `PERSONNEL_FILES_REVIEW` или существующий `HR_ENROLLMENT_MANAGER` позволяет подавать, проверять, скачивать и печатать в области конкретного действующего разрешения. Учитываются `GLOBAL`, `ORG_UNIT` и `SELF`, период, ресурс `*`/`personnel_files` и активность назначения.
- Сисадмин и помощник с `ASSISTANT_HR_SUPPORT` видят содержимое и историю в организации, включая неопубликованные версии, но не наследуют кадровое одобрение и экспорт из технической роли.
- Ресурсный `NONE` в соответствующей области запрещает служебный доступ; право владельца на свои файлы сохраняется.
- Неопубликованные и исторические версии доступны владельцу, кадровику и техническим специалистам. Руководителям — только одобренная действующая версия.
- Доступ к существующей полной кадровой карточке по-прежнему регулируется её собственными правилами. Новое разрешение на файлы не расширяет состав остальных разделов досье.

Каждый запрос превью, оригинала, печати и истории проверяет права заново. В ответах списка нет физических путей и ключей хранилища. Зафиксированы загрузки, технические отказы, решения, замещения, просмотры, скачивания, запросы печати, история и отказы доступа. Журнал БД защищён от UPDATE и DELETE. Привилегии администратора самой БД остаются инфраструктурной границей доверия.

## Подключение в среде эксплуатации

Эти шаги не выполняются автоматически при запуске приложения или сборке.

1. Установить зависимости `requirements.txt`, включая PyMuPDF для разбора и растровых превью PDF.
2. После резервного копирования и проверки плана применить миграции `pfiles001`, `pfiles002` обычным порядком Alembic. Вторая добавляет связь с реестром и справочник соответствий без backfill прежних записей. В рамках облачной проверки миграции применяются только к изолированной тестовой БД; эксплуатационная БД не изменяется.
3. Назначить закрытый каталог `PERSONNEL_FILE_STORAGE_ROOT`. Без отдельного значения используется `reviewed-files` внутри `PERSONNEL_PHOTO_STORAGE_ROOT`. Каталог не должен обслуживаться nginx или статической раздачей. Исходники и превью хранятся с ограниченными правами ОС; резервировать их следует согласованно с БД.
4. Установить антивирус с актуальными сигнатурами. По умолчанию вызывается `clamscan --no-summary`; `PERSONNEL_FILE_SCAN_COMMAND` позволяет указать команду совместимого сканера. Аргументы передаются без shell; код 0 означает чистый файл, 1 — угрозу, остальные коды и тайм-аут — недоступность проверки. Отсутствующий сканер не позволяет загрузку: HTTP 503, без публикации. Тестовая заглушка применяется исключительно в фикстурах.
5. Назначить явные разрешения и области через действующий механизм access grants. Проверить все семь категорий и постороннего пользователя на вымышленных файлах. Новые коды включены в каталог разрешений приложения.
6. Согласовать сроки хранения до реализации физического уничтожения. Новые файловые записи и аудит блокируют штатное удаление физлица; защищённые процессы очистки тестовых данных не должны обходить эти зависимости. Старые утверждённые каталожные fingerprints не пересчитываются автоматически.

Лимиты: исходник до 10 МиБ, до 20 страниц; фото лица JPEG 600 × 800 до 500 КиБ; JPEG/PNG декодируются, проверяются размер изображения и число кадров. PDF с шифрованием, восстановлением после повреждения, вложениями, сценариями, формами и активными действиями отклоняется. Оригинал получает SHA-256, превью — отдельные контрольные суммы. Полный multipart-запрос ограничен до парсинга, включая chunked-запросы без Content-Length. PDF-превью формируются с ограниченным разрешением; оригинал остаётся неизменным.

## Совместимость

Существующие фото не переносятся и не объявляются вновь проверенными. Пока новое фото не одобрено, карточка продолжает показывать старое каноническое фото. После первого одобрения новый процесс становится источником фото карточки. Отзыв управляемого фото не возвращает старое каноническое фото. Кадровая PDF-карточка запрашивает фото с `for_export=true`; сервер отдельно проверяет кадровое право экспорта, чтобы технический доступ к просмотру не раскрывал фото через выгрузку карточки. При отказе PDF формируется без фото.

Старый POST `/api/ppr/persons/{person_id}/photo` теперь только подаёт на проверку; для замены следует использовать новый интерфейс с точным идентификатором версии и revision. Публичная анкета и процесс приёма сохраняют свои прежние правила и не служат загрузкой в новый файловый контур.

Файлы размещаются в серверном хранилище, а не в ChatGPT Page: облачная Page содержит руководящий документ. Выбор облачного диска или объектного хранилища для эксплуатации требует отдельной инфраструктурной настройки; произвольные публичные ссылки не используются.

## Проверки

Целевые backend-тесты используют отдельную одноразовую PostgreSQL `corpsite_test` на loopback, минимальную контрактную схему и реальные SQL-транзакции. Производственная/прикладная БД и реальные документы не используются. Родительские fixtures общего набора исключаются через `--confcutdir=tests/personnel_files`; URL проверяется до подготовки данных. Фикстуры создают таблицы только в пустой изолированной БД; повторный запуск требует нового одноразового контейнера либо очистки именно этого тестового контейнера.

Пример запуска после создания выделенной БД и задания `TEST_DATABASE_URL` и такого же `DATABASE_URL`:

```bash
CORPSITE_SKIP_DOTENV=1 PYTHONPATH=. .venv/bin/pytest -o addopts='' --confcutdir=tests/personnel_files tests/personnel_files -q
cd corpsite-ui
npx vitest run app/directory/personnel/_components/PersonnelFilesPanel.test.tsx
NEXT_PUBLIC_API_BASE_URL=/api npm run build
```

Для проверки всей цепочки миграций из чистого checkout используйте **другую пустую** локальную БД с именем, заканчивающимся на `_test`, и явно задайте её URL через `TEST_DATABASE_URL`:

```bash
CORPSITE_SKIP_DOTENV=1 PYTHONPATH=. python scripts/personnel_files/verify_migrations.py
```

Проверяющий скрипт отказывается работать с непустой или нелокальной БД и не очищает данные. Исторические миграции i6/j7 требуют кадровую роль, действующего автора аудита и подразделение DISP; скрипт создаёт только эти вымышленные предпосылки в тестовой БД между историческими этапами. Учётные данные для входа не создаются. Затем проверяются переход до `pfiles002`, повторный `upgrade head`, неизменность прежних статусов и сроков, отсутствие догадок о классификаторе и автоматических назначений новых разрешений. Без исторических предпосылок один `alembic upgrade head` на пустой БД останавливается до миграций файлового модуля.

Проверены настоящие JPEG/PNG/PDF с вымышленным содержимым, отклонение активного PDF, шифрования и превышения лимитов, отсутствие сканера, доступ до/после одобрения, прямой запрос без токена, запрет экспорта руководителям и техническим ролям, отзыв подчинённости/разрешения, конкурирующие решения, точная версия при замене, повреждение оригинала/превью, очистка после ошибки транзакции, аудит, уведомления и отдельное изменение ФИО. Тестовая схема не заменяет проверку всей цепочки исторических миграций и nginx в целевой среде.
