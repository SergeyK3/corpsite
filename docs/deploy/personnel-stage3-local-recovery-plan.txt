Подготовка третьего этапа для рабочей ЛОКАЛЬНОЙ corpsite — 2026-10-07
Статус: после отдельного разрешения применено к рабочей локальной corpsite.
Отметка Alembic hrlocal301 установлена самим проверенным upgrade отдельного графа.
Исторические исходные условия и порядок подготовки ниже сохранены для аудита.
Повторно выполнять переход или генератор исходного снимка после применения нельзя.

1. Фактическое состояние и препятствия

Проверено READ ONLY на loopback corpsite: отметка Alembic za0b1c2d3e4f,
236 таблиц public, 8 версий шаблонов шести видов, 1245 приказов, 2029 пунктов,
574 кадровых события. Названия непустые, номера версий не конфликтуют.
Защитный триггер публикаций включён; старые индексы соответствуют hrtpl001.
Отсутствуют personnel_order_templates, versions.template_id,
orders.selected_template_version_id и LEAVE.ANNUAL.RECALL в обоих CHECK вида приказа.

org_units.name_kk/document_genitive_kk уже существуют как nullable TEXT.
personnel_section_settings уже создана вручную без изменения Alembic; структура,
ограничения и единственная строка проверены. Общий язык сейчас ru.
Обычная hrlang001 повторно создаёт таблицу и поэтому завершится ошибкой.
job_positions_catalog/position_job_catalog отсутствуют, но для этого перехода
не требуются: создание использует существующие кадровые назначения.

В текущих исходниках и проверенной истории Git нет определения za0b1c2d3e4f.
alembic history -r za0b1c2d3e4f:hrrecall001: Can't locate revision.
В старых дампах найдена такая же отметка; дамп подтверждает состояние, но не содержит
Python-файл миграции, её родителей или исходные операции. Место этой ревизии
в канонической цепочке НЕ установлено. Основной граф имеет головы hrrecall001
и jobcat001. upgrade heads затронет несогласованную ветвь должностей.
Поэтому прежний план прямого orgkk001 -> hrlang001 -> hrtpl001 -> hrrecall001
недостаточен для рабочей БД. stamp и выдуманная пустая старая миграция не подходят.

2. Конкретный путь восстановления

Если будет найден подлинный старый исходник: восстановить файл za0b1c2d3e4f
и родителей, сопоставить операции с физической схемой на копии БД, подготовить
проверяемое принятие уже созданной таблицы языка. Сейчас такой исходник не найден.

Подготовленная альтернатива — ОТДЕЛЬНЫЙ локальный граф:
    наблюдаемое исходное состояние za0b1c2d3e4f -> hrlocal301
Файлы: scripts/personnel_stage3_local_recovery/{alembic.ini,env.py,versions/*.py}.
Это проект принятия проверенного физического снимка, а не восстановленная история.
Он находится вне основного alembic/versions и не включён в серверный ZIP.
Файл исходного состояния запрещает upgrade с пустой БД и downgrade. Новая hrlocal301
действительно выполняет DDL hrtpl001/hrrecall001, загружая проверенные исходные файлы.
Отметки этих канонических ревизий и их неизвестных предшественников не назначаются.

Перед DDL сверяются отметка, колонки (типы, длины, nullability, default), ограничения,
индексы, триггеры затронутых таблиц, состав public-таблиц и SHA256 строк ВСЕХ старых
таблиц. Несовпадение останавливает переход до DDL. Изменившиеся после подготовки
данные требуют свежего архива и нового рассмотренного снимка, а не обхода проверки.
Существующие orgkk/hrlang-объекты принимаются по физической проверке; язык сохраняется.
Переход выполняется одной транзакцией с блокировкой versions/orders/items,
lock_timeout=5s, statement_timeout=120s. После DDL сравниваются все старые строки,
исключая только два добавленных столбца. Alembic сам обновляет отметку на hrlocal301
после успешного upgrade; отдельного UPDATE alembic_version или stamp нет.

Этот вариант истории нужно явно рассмотреть до применения. hrlocal301 принадлежит
отдельному графу: дальнейшие локальные миграции обязаны использовать его до отдельного
согласования общей истории. Обычный основной alembic upgrade head после него не подходит.
Автоматического объединения с канонической ветвью нет: оно признало бы неизвестные
предыдущие операции выполненными. Для сервера этот локальный путь не предлагается.

7. Дефект формы создания и причина пустой должности KZ

Зафиксирован дефект: canSubmit объединял множество условий, но возле неактивной
кнопки не объяснял их. Исправлено в PersonnelOrderCreateDialog: перечень причин
рядом с кнопкой строится из тех же условий, которыми она блокируется. Он включает
ограничение схемы, выбранную версию, сотрудника, номер/даты, обязательные RU/KZ-поля,
основания, документные формы, даты/номер свидетельства и неправильный период.
Причины локализованы RU/KZ и связаны с кнопкой через aria-describedby. Недоступность
независимых вариантов остаётся неблокирующим сообщением для прежних видов.

В рабочей БД подбор Мусабекова возвращает трёх активных сотрудников. Для Бейбита
Амантаевича (employee_id=29) API возвращает должность №71 «Заведующий отделением
химиотерапии 1», name_kk=null и job_namekk=null; запись справочника подтверждает
отсутствие перевода. Также нет name_kk для должностей №6 и №1 других результатов.
Это отсутствие справочного перевода, а не потеря существующего KZ-текста в форме.
«Должность KZ» остаётся свободным редактируемым полем; добавлено конкретное пояснение.
Перевод не придумывается автоматически; справочник и рабочая БД не изменяются.
52 теста формы/автозаполнения прошли; TypeScript-проверка без ошибок.
В реальном браузере 3000 под существующим ADMIN выбран employee_id=29 через
подбор; русская должность заполнена, отсутствие перевода подтверждено, ручной ввод
KZ проверен. Причины заполненных полей исчезают, ограничение схемы остаётся возле
кнопки. Запросов записи не было. Отчёт form3000-result.json и снимок
create-blockers3000.png находятся в runtime/personnel-stage3-preparation/.
Новые UI-изменения нужно включить в окончательный код и пакет после согласования
коммита; существующий ZIP на данном этапе не пересобирался.
