posdir001: policy v2 — сохранение форм без автоматического confirmed

АКТУАЛЬНОЕ РЕШЕНИЕ

Каноническая posdir001 теперь использует position_directory_review_migration:
значения сохраняются, оба статуса ВСЕХ 111 записей — needs_review. Автоматически
confirmed=0. Никаких новых переводов и падежных форм не придумывается.

Сначала выполнен read-only аудит всех 10 доступных БД настроенного локального
PostgreSQL-кластера. Каноническая posdir001 нигде не применена. Эквивалентная
старая схема уже применена через hrlocal303 в четырёх БД:
corpsite, corpsite_position_directory_709afeb6_test,
corpsite_position_directory_a0dc1a8b_test, corpsite_supplementary_percent_bed7548d_test.
Подробности: posdir001-local-db-audit-20261026.json.
В corpsite сейчас 141 должность, 113 confirmed-переводов и 112 confirmed-форм.
История не позволяет надёжно отделить автоматические подтверждения от ручных.
Непустое значение, совпадение со справочником и revision=1 не являются доказательством.

Поэтому helper app/db/position_directory_migration.py оставлен БЕЗ изменений
для уже применённой локальной ветки. Изменён только ещё не применённый canonical
entry point posdir001: он вызывает отдельный helper v2. Последняя разрешённая
production-сверка показала podup001; в этой задаче production не подключался.

ПОЛИТИКА И ПОВТОРЯЕМОСТЬ

Первоначальный v2 сохраняет прежние заполненные тексты и классификацию, ставит
needs_review и пишет транзакционный receipt в комментарий position_directory:
posdir001:forms-needs-review:v2. Промежуточное выполнение старого helper не
становится видимым другим транзакциям с confirmed: весь запуск — одна транзакция.
Непустое существующее name_kk сохраняется точно, включая пробелы.

При receipt v2 повтор — полный no-op: не сбрасывает поздние ручные confirmed,
не восстанавливает очищенные поля, не создаёт синонимов и не расходует sequence.
Несогласованный receipt/неполная схема блокируется. Старая схема без receipt
блокируется ДО изменений: никакого автоматического reset, stamp или повторного ALTER.

Для старой hrlocal303 есть отдельный review_existing_directory(connection, manifest).
Он требует owner_approved=true, policy v2, покрытие ВСЕХ строк ровно один раз,
точные before (ID, названия, категории, формы, revision, статусы) и отдельные
решения по двум статусам. Сохраняемый confirmed допустим только с непустым
значением и явной confirmation_evidence. Весь набор проверяется под FOR UPDATE
до первой записи. Дрейф, неполный набор и пустое подтверждение вызывают отказ.
Меняются только статусы и revision изменённых строк, тексты/IDs/связи сохраняются.
Receipt обеспечивает безопасный повтор и сохранение последующих ручных решений.
Этот переход проверен ТОЛЬКО в изолированной БД; постоянные локальные БД не менялись.
Так обе ветки используют одну политику: автоматически загруженное — needs_review,
confirmed — только явное ручное решение. Пока нет проверенного manifest, старая
локальная БД намеренно остаётся неизменной; слепой сброс был бы потерей согласований.

ПРОВЕРКИ

Реальные SQL выполнялись только в новых случайных loopback *_test БД. Копировались
четыре справочника; кадровые FK/снимки синтетические, реальные персональные строки
не выгружались. Проверены все значения, статусы, пустоты, повторный no-op,
поздние ручные confirmed/очистка, отказ на legacy, адресный переход с сохранением
явного подтверждения и отказ при дрейфе/неполном или неподтверждённом manifest.
Существующие тесты справочника переведены на canonical v2.
Итог: 21 тест прошёл на экспорте ровно подготовленного индекса Git, без
посторонних рабочих изменений. Реквизиты подключения в экспорте не сохранялись;
для записи использовались только новые случайные тестовые БД.
Повторный read-only контроль четырёх постоянных hrlocal303 БД подтвердил
прежние revision и количества статусов; переход в них не выполнялся.

BACKUP / RESTORE: ОБНОВЛЁННАЯ ИНСТРУКЦИЯ

1. Перед отдельно разрешённой операцией согласовать конкурирующие записи,
   сделать проверенный полный backup БД, schema, counters, Alembic revision,
   policy receipt и зафиксировать версию КОДА. Scoped backup четырёх справочников
   не заменяет полный production backup. Восстановить backup в отдельной БД и проверить.
2. До COMMIT: ошибка => ROLLBACK. В тесте вернулись все строки и schema, но
   nextval существующей sequence синонимов НЕ откатился: возможен пропуск номера.
   Не сбрасывать sequence без проверки ссылок и конкурирующих записей.
3. После COMMIT штатный downgrade ПО-ПРЕЖНЕМУ отказывает:
   «Position directory rollback requires an explicit data-preserving plan».
   Не удалять новые колонки с ручными формами/согласованиями и не стирать receipt
   ради повторного backfill. В тесте отказ downgrade не изменил мигрировавшие данные.
4. В другой новой БД восстановлена исходная копия: совпали schema, constraints,
   строки, counters и синтетические защищённые записи. Это scoped rehearsal,
   а не полная production-репетиция со всеми данными/нагрузкой. После новых записей
   нужен отдельно согласованный обратный план или restore с сохранением изменений
   после backup. Receipt должен соответствовать восстановленной версии кода.
5. Для hrlocal303: сначала read-only снимок, явная проверка происхождения confirmed,
   одобренный manifest, репетиция на отдельной копии; не массовый автоматический reset.
6. После отдельно разрешённой production-миграции — новый снимок и пересчёт
   переноса. Старые confirmed в локальной инвентаризации не доказывают ручное
   утверждение; нельзя автоматически вернуть их поверх needs_review новой схемы.

Временные БД удалены. Production, постоянные локальные БД, исходная инвентаризация,
owner approvals и текущий план переноса не изменены.
