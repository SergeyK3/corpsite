4. Проект адресного повторно запускаемого переноса

Планировщик scripts/plan_personnel_dictionary_transfer.py работает только
с JSON-файлами, не подключается к БД, не содержит apply и не исполняет SQL.
Команда воспроизведения текущего плана:

python scripts/plan_personnel_dictionary_transfer.py
  --inventory reference-data/dictionaries/local-review-20261026.json
  --production runtime/production-dictionary-data-20261026.json
  --schema runtime/production-dictionary-schema-20261026.json
  --approvals docs/deploy/personnel-dictionary-owner-approvals-20261026.json
  --existing-plan docs/deploy/personnel-dictionary-production-plan-20261026.json
  --output docs/deploy/personnel-dictionary-production-plan-20261026.json

--existing-plan ограничивает повторную сверку утверждёнными должностями и их
зависимыми связями; исходный план и снимки проверяются по fingerprint. Тот же
адресный запуск повторяем: не создаёт второй записи решения или дублей плана.

Перед будущим запуском подготовить новый адресный план по свежему read-only
снимку после согласованных миграций. Не применять сегодняшний plan к другой
схеме или изменившимся данным. Зафиксировать SHA, хеш исходного набора,
схему и свежие before-значения всех изменяемых полей. Разрешить только явно
утверждённые ADD/UPDATE; MATCH пропускать; CONFLICT/MANUAL останавливают пакет.

Контракт будущего исполнителя:
- Одна транзакция. Сначала группы и виды, затем должности/специальности,
  потом синонимы/связи. Проверить уникальные ключи, входящие FK и триггеры,
  отсутствие побочных записей в защищённые таблицы. Блокировать строки
  справочников в устойчивом порядке; при конкурирующем изменении остановиться.
- SELECT по устойчивому ключу должен вернуть ровно одну строку для UPDATE.
  Сравнить before по всем затрагиваемым полям и текущую target revision,
  если она есть. Чужие изменения не перезаписывать. При изменении категории
  нужен отдельно утверждённый старый ключ; сам planner это не угадывает.
  Для ID 24/52 old key задан в existing_key/match_key (other), конечный key —
  technical. Сначала проверить target ID и before; после UPDATE разрешать
  зависимые связи через post_update_key на том же ID, не искать дубль other.
- INSERT без source ID: identity/sequence целевой БД выдаёт новый ID. Все
  FK разрешать заново через group.code, job_code и согласованный ключ должности.
  Не копировать source revision, created_at и любые внутренние числовые IDs.
- Если desired уже достигнуто, SKIP без обновления timestamp/revision.
  При реальном изменении revision увеличивается по правилам target API.
  Повторный запуск того же утверждённого набора даёт пропуски, а не дубли.
- Не менять employees, person_assignments, приказы, пункты, историю применения,
  снимки, шаблоны. Не удалять отсутствующие в наборе production-строки.
  Архив специальности — только is_active=false, с сохранением существующих FK.

Проверка: сравнить desired/actual по смысловым ключам, отсутствие новых
дубликатов и потерянных связей; проверить все 11 синонимов, 55 активных/6 архивных
специальностей и 3 группы, сохранение needs_review. В изолированной репетиции
проверить поиск RU/KK, сохранение/повторное открытие приказа и повторный запуск
переноса. Контроль защищённых таблиц — контрольные суммы/количества и адресный
аудит записей без выгрузки персонального содержимого в отчёт. Учитывать обычные
конкурентные изменения приложения: окно проверки/операции согласовать отдельно.

Откат: до COMMIT любая ошибка => ROLLBACK всей транзакции. Перед будущим
применением сохранить проверенную резервную копию и отдельный журнал before/
after только затронутых строк/связей. После COMMIT — новый адресный обратный
план, восстанавливающий before только при совпадении текущего значения с after.
Новые записи можно удалять лишь после проверки ВСЕХ входящих ссылок и наличия
отдельного разрешения; при появившихся ссылках остановиться, а не каскадировать.
Автоматический downgrade схемы с удалением форм/переводов не использовать.

Планировщик проверен десятью синтетическими тестами без БД/сети: разные локальные
и целевые IDs, сохранение неподтверждённых состояний, конфликт категорий,
недостающая схема, повторяемость и неоднозначные исходные ключи. Дополнительно
проверены утверждённая смена категории с сохранением before, существующей
identity, связи и синонима, отсутствие цели (INSERT запрещён), отсутствие связи,
конфликт другой связи, неверный target ID и повторная сверка конечного key.
