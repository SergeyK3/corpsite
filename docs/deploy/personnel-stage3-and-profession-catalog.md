# Третий этап и нормализованный справочник профессий

Содержит исправления после `e9b31404`: совместимость редактора со старой схемой,
создание приказа по конкретной опубликованной версии, ожидание загрузки вариантов,
причины блокировок и повторную загрузку. Дополнительно подключает утверждённые
названия профессий ко всем явно сопоставленным историческим должностям.
Сервер в рамках подготовки не изменялся; push не выполнялся.

## Источник и разделение данных

`reference-data/job-positions/catalog-v1.json` — переносимый справочник, извлечённый
только из `positions_catalog_review_v2.xlsx`, лист `catl_job`, таблица
`CatlJobPositionsV2`, диапазон `A1:E89`. SHA256 исходного XLSX указан внутри JSON.
Все 88 названий и 108 связей сохранены без самостоятельного перевода, сокращения
или подбора по похожему русскому названию. Другие листы Excel не импортируются.

`position_job_catalog.position_id → job_code → job_positions_catalog` определяет
профессию; действующее основное `person_assignments` определяет одновременно
историческую должность и подразделение. `positions`, `employees`, назначения,
исторические приказы и сохранённые документные тексты импорт не изменяет.

- RU/KZ-названия профессии: `job_nameru` / `job_namekk`.
- Подразделение RU/KZ: `org_units.name` / `name_kk` из того же назначения.
- Грамматическая форма должности: `job_namekk_doc`, отдельно от названия.
- Сохранённые и вручную уточнённые документные формы не заменяются при чтении.
- Без связи используется прежняя подстановка и доступно ручное уточнение.

Например, `positions[71] → CLINICAL_DEPARTMENT_HEAD` (строка 60 Excel) даёт
«Заведующий клиническим отделением» / «Клиникалық бөлімше меңгерушісі»;
«Химиотерапия 1» / «№1 химиотерапия бөлімшесі» берутся отдельно из подразделения 45.
Историческое имя должности 71 остаётся прежним. Ранее заполненное точным значением
из листа «Должности» поле `positions[71].name_kk` не является источником нового
справочника и не переносится отдельным UPDATE.

## Подготовленный серверный переход — не выполнен

Этот путь предназначен только для известной канонической истории Alembic.
Не использовать `stamp`, не подменять неизвестную старую ревизию. При неизвестной
ревизии, расхождении схемы или данных остановиться и исследовать её отдельно.
Локальный recovery-граф ниже на сервер не применять.

После отдельного разрешения на серверный перенос:

1. Проверить точный состав изменения относительно `e9b31404`, текущую ревизию
   (`python -m alembic current`) и единственную голову (`python -m alembic heads`).
   В этом наборе каноническая голова — `hrjobmerge001`.
2. Сделать и проверить резервную копию БД и исходников обычным серверным порядком.
   Резервные копии не входят в Git. Перед DDL сохранить контрольные суммы строк
   `positions`, `employees`, `person_assignments`, `org_units` и кадровых таблиц.
3. Проверить офлайн план канонических миграций относительно фактической ревизии.
   `hrjobmerge001` объединяет `hrrecall001` и `jobcat001`; merge не содержит DDL.
   `poskk001` добавляет только nullable `positions.name_kk`, `jobcat001` создаёт
   две пустые таблицы справочника и связей. Они не переименовывают записи.
4. В согласованное окно выполнить `python -m alembic upgrade hrjobmerge001`.
5. Сначала выполнить импорт без `--apply`:

   ```bash
   python scripts/import_job_catalog.py --report runtime/job-catalog-dry-run.json
   ```

   Проверить `missing_ids`, `conflicts`, `can_apply`, все связи и хеш JSON.
   Отсутствующий исторический ID или отличающаяся существующая связь/название
   блокируют импорт. Ничего не сопоставлять по догадке.
6. После проверки применить:

   ```bash
   python scripts/import_job_catalog.py --apply --report runtime/job-catalog-import.json
   ```

   Импорт атомарен; повторный dry-run должен показывать ноль изменений.
   Отличающиеся существующие значения сохраняются и блокируют повторный импорт.
7. Сравнить старые данные с сохранёнными контрольными суммами. Проверить API
   сотрудника и RU/KZ-формы на Мусабекове, медсестре, враче и экономисте, а также
   прежнее поведение несопоставленных должностей. Использовать штатный процесс
   развёртывания исходников; эта инструкция сама ничего не запускает.

JSON содержит справочные данные, без сотрудников, назначений и тестовых приказов.
Excel, ZIP, дампы, временные отчёты и тестовые БД переносить не требуется.

## Согласованный шаблон отзыва

`reference-data/personnel-templates/annual-leave-recall.json` переносится отдельно
через штатный редактор шаблонов. Все восемь согласованных текстовых полей сохранены.
Метаданные `variable_sources` поясняют источники переменных, но не являются
операцией импорта или публикации. Не синхронизировать и не заменять существующие
серверные версии автоматически. На localhost:3000 согласованная версия 8 / 13 уже
опубликована; локальные ID и статус публикации на сервер не копируются.

## Проверенный локальный путь

Рабочая локальная БД имела неизвестную каноническому графу ревизию
`za0b1c2d3e4f`. Проверенный отдельно переход `hrlocal301` создал структуру третьего
этапа без подмены канонической истории. Код и описание принятия физического
снимка сохранены в `scripts/personnel_stage3_local_recovery` и
`docs/deploy/personnel-stage3-local-recovery-plan.txt`. Исходные резервные копии,
снимки и временные отчёты намеренно не включены в коммит; первый recovery-переход
нельзя воспроизвести без отдельно проверенных исходных материалов.

Продолжение этого отдельного графа — `hrlocal302`: создание только двух таблиц
справочника. DDL и импорт 88/108 сначала проверены в транзакции с откатом, затем
применены локально. Все защищённые исторические строки, включая сохранённые тексты
и применения шаблонов, совпали до и после. Для локального импорта использованы
`--alembic-config scripts/personnel_stage3_local_recovery/alembic.ini`
и `--required-revision hrlocal302`. На сервер этот локальный граф не переносить
как действующую историю.
