Подготовка адресного переноса кадровых шаблонов, 181e750e
======================================================

Это инструкция для последующего согласованного переноса. В ходе подготовки
ни одна команда записи/деплоя ниже на сервере не выполнялась.
Для согласованной ветки reconcile/server-181e750e порядок подготовки нового
release-каталога и сохранения ВСЕГО старого каталога описан отдельно в
server-reconcile-181e750e.txt. Он имеет приоритет над прежним способом обновления
кода. Инструменты переноса и backup теперь включены в эту локальную ветку;
на сервер они ещё не отправлены. Адресный data-only пакет остаётся отдельным.

Каждая новая серверная identity получит собственную v1. Локальные номера
версий/ID сохранены как происхождение в JSON и плане, не навязываются серверу.
При обновлении существующей identity используется MAX(version_number)+1.

Экспорт: templates.json, ровно шесть записей, без приказов/людей/назначений/
оплаты/тестовых данных. Содержит названия RU/KK, код, is_default, восемь
текстов, based_on_built_in, статус, allowed/required variables, привязки
токенов к полям и флаги соответствующих контрактов. Исторические локальные
версии, audit user_id/время и copied_from_template_version_id не переносим:
это не рабочие настройки; автор публикации выбирается на сервере, а рабочие
тексты самостоятельны и не зависят от provenance FK.

Команды передачи пакета (PowerShell, только после разрешения на перенос):
  scp .\runtime\personnel-template-transfer-181e750e.tar.gz corpsite:/tmp/
  scp .\runtime\personnel-template-transfer-181e750e.tar.gz.sha256 corpsite:/tmp/

Серверная сессия bash: выполнить этапами, не запускать вслепую целиком.

  set -euo pipefail
  umask 077
  REPO=/opt/projects/corpsite/app
  PACK=/tmp/personnel-template-transfer-181e750e
  RECOVERY=/opt/projects/corpsite/template-transfer-backup-$(date -u +%Y%m%dT%H%M%SZ)
  TARGET=181e750ec9b9f945db4ad28323302edc25045892
  cd /tmp
  sha256sum -c personnel-template-transfer-181e750e.tar.gz.sha256
  test ! -e "$PACK"
  tar -xzf personnel-template-transfer-181e750e.tar.gz
  cd "$PACK"
  sha256sum -c SHA256SUMS
  mkdir -m 700 "$RECOVERY"
  cd "$REPO"
  export PYTHONPATH="$REPO"
  export PYTHONDONTWRITEBYTECODE=1

Сохранение источников и старого состояния (данные остаются на сервере):
  git rev-parse HEAD > "$RECOVERY/git-head.txt"
  git status --porcelain > "$RECOVERY/git-status.txt"
  git diff --binary HEAD > "$RECOVERY/server-worktree.patch"
  git diff --cached --binary > "$RECOVERY/server-index.patch"
  tar --exclude=node_modules --exclude=.next --exclude=__pycache__ \
      --exclude='*.env' --exclude='*.env.*' --exclude='*.pyc' \
      -czf "$RECOVERY/server-sources.tar.gz" \
      app alembic corpsite-ui scripts requirements.txt alembic.ini
  .venv/bin/python "$PACK/scripts/personnel_template_transfer_snapshot.py" \
      > "$RECOVERY/server-before.json"

Окно обслуживания: остановить backend/frontend и убедиться, что нет других

Миграция изменённой уникальности номера+даты обязательна для кода 181e750e.
Она не импортирует шаблоны. Проверить текущую ревизию/группы ещё раз:
  .venv/bin/python "$PACK/scripts/personnel_template_transfer_snapshot.py" \
      > "$RECOVERY/server-pre-migration.json"
  .venv/bin/alembic current
  .venv/bin/alembic heads
  # Ожидание до: hrjobmerge001; head нового кода: podup001.
  # Если ревизия/группы отличаются — STOP, отдельно разобраться, не stamp.
  .venv/bin/alembic upgrade podup001
  .venv/bin/alembic current

Новый план после миграции обязателен: старый план специально не применим к
изменившейся схеме/состоянию. plan выполняется в READ ONLY. JSON и таблицу
проверить; ready должно быть true, ambiguities пустым. Ожидаем CREATE шесть
раз, пять PUBLISHED и DRAFT у ключа 24; IDs назначатся на сервере.
  .venv/bin/python "$PACK/scripts/transfer_personnel_templates.py" plan \
      --bundle "$PACK/templates.json" --output "$RECOVERY/plan.json"
  .venv/bin/python -m json.tool "$RECOVERY/plan.json"

Если появились кандидаты: JSON содержит конкретные server IDs, код, оба
названия, текущие версии и content_sha256. Не сопоставлять по локальным ID.
Сформировать отдельно проверенный mapping.json, например:
  {"28":{"server_template_id":123,"candidate_sha256":"HASH OF candidate(...)"}}
123 — именно проверенный серверный ID, не образец для исполнения. Хеш вычисляет
scripts.transfer_personnel_templates.candidate(template, versions) и digest(...)
на свежем snapshot, не хеш только номера ID. Затем plan --mapping mapping.json.
Два локальных самостоятельных шаблона не могут сопоставляться одному серверному.

Импорт (ТОЛЬКО после просмотра нового плана и разрешения на запись):
  .venv/bin/python "$PACK/scripts/transfer_personnel_templates.py" apply \
      --bundle "$PACK/templates.json" --plan "$RECOVERY/plan.json" \
      --actor-login admin \
      --backup "$RECOVERY/affected-templates-before.json" \
      --receipt "$RECOVERY/import-receipt.json"

admin — прочитанный существующий активный серверный логин; его следует
подтвердить как автора операции. Локальные user_id не используются.
Затронутые identities/версии сохраняются в backup до любых изменений.
Для текущего CREATE-плана backup пуст по этим таблицам: старые пять identities
не затрагиваются, receipt перечислит новые шесть IDs для адресного отката.
Таблицы шаблонов заблокированы на время одной транзакции. При ошибке — rollback.
Старые версии не удаляются/не переписываются: нужная активная версия архивируется,
новая получает следующий номер. Несвязанный черновик не затрагивается при
публикации новой версии. Ссылки и тексты приказов не изменяются.

Проверка после импорта и повторного запуска без записи:
  .venv/bin/python "$PACK/scripts/personnel_template_transfer_snapshot.py" \
      > "$RECOVERY/server-after.json"
  .venv/bin/python "$PACK/scripts/transfer_personnel_templates.py" plan \
      --bundle "$PACK/templates.json" --output "$RECOVERY/repeat-plan.json"
  .venv/bin/python -m json.tool "$RECOVERY/repeat-plan.json"
Ожидание: шесть NO_CHANGE. При повторном apply сначала нужен новый plan и новые
имена backup/receipt; новых identities/версий не будет. Старые receipt/backup
не перезаписывать. Receipt содержит фактически выделенные серверные IDs.
Если применялось явное mapping, receipt.repeat_mapping содержит обновлённые
хеши выбранных записей. Сохранить этот объект в отдельный mapping-repeat.json
и передать plan --mapping "$RECOVERY/mapping-repeat.json"; старые хеши до
импорта намеренно перестают соответствовать изменившимся версиям.

тоже существуют, но здесь миграция/build/рестарты разделены вокруг переноса,

Адресное восстановление шаблонов (maintenance window, до новых использований):
  sudo systemctl stop corpsite-backend corpsite-frontend
  .venv/bin/python "$PACK/scripts/transfer_personnel_templates.py" restore \
      --backup "$RECOVERY/affected-templates-before.json" \
      --receipt "$RECOVERY/import-receipt.json"
  # Сначала просмотр без записи. После решения восстановить:
  .venv/bin/python "$PACK/scripts/transfer_personnel_templates.py" restore --apply \
      --backup "$RECOVERY/affected-templates-before.json" \
      --receipt "$RECOVERY/import-receipt.json"
Восстанавливаются только names/status/updated_at затронутых старых записей и
удаляются только новые НЕИСПОЛЬЗОВАННЫЕ identities/версии. Проверяются SHA,
состояние после импорта, ссылки из приказов/applications/provenance. Если новая
версия уже использована, скрипт откажет: нельзя удалять её либо менять приказ;
нужен отдельно согласованный исправляющий импорт с новой версией. Счётчики
sequence назад не переводятся. Откат 181e750e и старых локальных патчей кода
выполняется отдельно по сохранённым git-head/patch/source архиву, без --hard.

Полный restore базы — только аварийный вариант после отдельного решения,
при остановленных ВСЕХ writers и отсутствии более поздних данных, которые
требуется сохранить. Он восстановит и схему, и старое ограничение, и данные:
  .venv/bin/python "$PACK/backup/database_backup_restore.py" verify \
      --repo "$REPO" --file "$RECOVERY/corpsite-before.dump"
  .venv/bin/python "$PACK/backup/database_backup_restore.py" restore \
      --repo "$REPO" --file "$RECOVERY/corpsite-before.dump" --confirm-restore corpsite
Это НЕ обычный откат только шаблонов: полная база public+staging заменяется
одной транзакцией. Нельзя выполнять его поверх новых приказов. Не отключать
FK/триггеры. alembic downgrade hrjobmerge001 отдельно допустим только после
проверки, что вновь разрешённые одинаковые номера разных дат не появились;
сам downgrade podup001 остановится при невозможности старой уникальности.

SHA и сведения о проверках находятся в report.json и SHA256SUMS пакета.
Остаётся нерешённой подготовка согласованного серверного кодового дерева.
Общий tsc имеет отдельный долг в тестовых файлах, но штатная сборка успешна.
Подготовка не выполняет commit/push, запись в серверную БД или деплой.
