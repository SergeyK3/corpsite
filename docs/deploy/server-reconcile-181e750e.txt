Пункт для явного решения: политика удаления шаблонов
--------------------------------------------------
Кандидат сохраняет уже существующее поведение 181e750e:
обычный диалог подтверждения; default можно удалить/архивировать; шаблон,
на который ссылается приказ/application, автоматически архивируется, его

copied_from provenance; собственные тексты/версии копий остаются.

ввести название; использованный шаблон (включая copy provenance) сначала
получает TEMPLATE_IN_USE, затем нужно отдельно выбрать архивирование.
Сервер также ограничивает echo-названия в delete request длиной 200 символов;
новый код допускает удаление существующего длинного заголовка.

Нужно подтвердить сохранение поведения 181e750e либо вернуть серверную политику
с согласованными изменениями API/UI и повторными тестами. До такого решения
ветка является проверяемым кандидатом. Оба варианта сохраняют приказы; нельзя
под видом разрешения конфликта менять опубликованные тексты исторических версий.

Безопасный порядок обновления серверного каталога
------------------------------------------------
Не делать git pull/reset/checkout в текущем грязном /opt/projects/corpsite/app.
Новый код готовится в отдельном чистом release-каталоге. Старый каталог целиком
сохраняется, включая .git, .env, .venv, node_modules, runtime, backups и все
неотслеживаемые файлы. После остановки writers путь app переключается на новый
каталог symlink. Ничего из старого каталога не удалять.

Подготовленный git bundle содержит ветку и её историю без push. SHA и hash
финального коммита указаны в локальном release.json. Передача ниже — только
после разрешения на обновление; snapshot/production report не передаются
как исходники приложения.

PowerShell:
  scp .\runtime\server-reconciled-181e750e.bundle corpsite:/tmp/
  scp .\runtime\server-reconciled-181e750e.bundle.sha256 corpsite:/tmp/

Bash на сервере, этапами:
  set -euo pipefail
  umask 077
  BASE=/opt/projects/corpsite
  APP="$BASE/app"
  BUNDLE=/tmp/server-reconciled-181e750e.bundle
  BASE_COMMIT=5ecc5d8154f30d5ae0316df558a078d03a46b8e6
  RELEASE_REF=refs/heads/reconcile/server-181e750e
  cd /tmp
  sha256sum -c server-reconciled-181e750e.bundle.sha256
  RELEASE=$(git bundle list-heads "$BUNDLE" "$RELEASE_REF" | awk '{print $1}')
  test -n "$RELEASE"
  STAMP=$(date -u +%Y%m%dT%H%M%SZ)
  NEW="$BASE/releases/$RELEASE"
  OLD="$BASE/server-before-$STAMP"
  RECOVERY="$BASE/recovery-$STAMP"
  test -d "$APP" && test ! -L "$APP"
  test "$(readlink -f "$APP")" = "$APP"
  test ! -e "$NEW" && test ! -e "$OLD" && test ! -e "$RECOVERY"
  test "$(git -C "$APP" rev-parse HEAD)" = "$BASE_COMMIT"
  mkdir -m 700 "$RECOVERY"
  mkdir -p "$BASE/releases"

Восстановление
--------------
При ошибке остановить всех writers/timer, сохранить новые диагностические
данные и receipt. Сначала read-only preview адресного restore шаблонов:
  cd "$NEW"
  .venv/bin/python scripts/transfer_personnel_templates.py restore \
      --backup "$RECOVERY/templates-before.json" --receipt "$RECOVERY/import-receipt.json"
  # --apply — только после проверки; importer откажет при новых ссылках/дрейфе.

Возврат кода: подготовить отдельную ссылку app.rollback-$STAMP на OLD и
переключить APP через mv -T при остановленных сервисах. NEW и OLD сохранить,
ничего не сбрасывать git reset --hard. Внимание: старый backend рассчитан на
старую уникальность order_number. Нельзя запускать его после появления новых
одинаковых номеров разных дат без отдельного согласования схемы/данных.
Полный DB restore — только при отдельном разрешении и отсутствии новых данных,
которые требуется сохранить. Он заменяет public+staging одной транзакцией;
не выполнять его поверх новых приказов. Инструкция backup/restore и downgrade
подробно описана в personnel-template-transfer-181e750e.txt.

Не удалять OLD, RECOVERY, резервную копию DB, git patch, оригинальные каталоги
и производственный отчёт после успешного переключения: срок хранения решается
отдельно. Push, импорт, scheduler, переключение каталогов и деплой в текущем
задании не выполнялись.
