# ADR-066 — Интеграция классификатора кадровых событий v1.1 с кадровым журналом

**Статус:** Draft — Ready for Architecture Review  
**Дата:** 2026-08-24  
**Решение:** канонический versioned registry в коде, с единой публикацией его данных в DB validation, API и UI. Коды неизменны во времени; версия registry в `employee_events` не хранится.

## 1. Контекст и проблема

Кадровый журнал `/directory/personnel/journal` должен вести фактически оформленные кадровые факты. Нужна совместимая интеграция классификатора v1.1, прежде всего для отпусков, без смешения таких фактов с состояниями документооборота и без переименования существующей истории.

## 2. Фактическое состояние

Журнал читает `public.employee_events`; его основной идентификатор — `event_type TEXT NOT NULL`. DB `CHECK` допускает `HIRE`, `TRANSFER`, `POSITION_CHANGE`, `RATE_CHANGE`, `CORRECTION`, `TERMINATION`, `EMPLOYEE_ENROLLED_FROM_IMPORT`. Frontend и backend используют независимые жёсткие списки. `event_class` является укрупнённым техническим классом, а не классификатором.

Приказные события создаются при apply приказа в `SIGNED` или `REGISTERED`; `order_id` и `order_item_id` физически имеются, но журнал возвращает только `order_ref`. Проект, ожидание подписи и прочие стадии workflow в журнал не пишутся. Отпускных writers нет. Записи `VOIDED` могут попасть в текущую выборку.

## 3. Термины

- **Канонический код** — конечный стабильный `event_type`, определённый registry. Его семантика не изменяется после публикации.
- **Версия registry** — версия неизменяемого manifest/набора определений. Новая версия может добавлять коды и отображаемые данные, но не меняет семантику уже опубликованного кода.
- **Legacy-код** — устаревшее значение, более не разрешённое для новых записей, но читаемое исторически.
- **Алиас чтения** — отображаемое/интерпретируемое соответствие legacy-кода каноническому, не переписывающее строку.
- **Исходный отпуск** — событие предоставления (`GRANT`), к которому относится изменение периода или досрочное прекращение.
- **Фактический период** — результат последовательного применения действующих событий одной отпускной цепочки.

## 4. Границы решения

Решение определяет контракт `employee_events`, registry, связи с приказом и последующую адаптацию API/UI. Оно не проектирует заявления, согласования, ЭП, календарь и расчёт отпусков, табель, замещение или UI оформления приказа. Эти системы могут передавать основания и инициировать приказ, но не создают journal-event до фактического apply.

## 5. Каноническая модель события

`employee_events.event_type` хранит ровно один конечный код. Новые записи используют только коды, разрешённые текущим registry, например `LEAVE.ANNUAL.RECALL`. Отдельные физические поля category, leave kind и operation не вводятся: они детерминированно выводятся из registry.

В строке не хранится `registry_version`. Вместо этого code является постоянным идентификатором: нельзя изменить его категорию, операцию, правила воздействия или прежнее значение. Изменение семантики требует нового кода. Registry-version хранится и публикуется как metadata самого registry/release, применяется для аудита конфигурации и API-кэширования, но не требуется для интерпретации исторической строки.

Для каждого кода registry содержит: версию, код, категорию, `label_ru`, `label_kk`, класс воздействия, признак изменения snapshot, допустимость прямого создания, признак «только через приказ», а для отпусков — `leave_kind`, `operation`, признак обязательного `source_event_id` и допустимые типы источника.

## 6. Модель отпускных событий

Формат: `LEAVE.<leave_kind>.<operation>`. Минимальный v1.1 набор:

```
LEAVE.ANNUAL.GRANT
LEAVE.ANNUAL.POSTPONE
LEAVE.ANNUAL.EXTEND
LEAVE.ANNUAL.RECALL
LEAVE.UNPAID.GRANT
LEAVE.UNPAID.EARLY_RETURN
LEAVE.PAID_OTHER.GRANT
LEAVE.MATERNITY.GRANT
LEAVE.CHILDCARE.GRANT
LEAVE.UNCLASSIFIED
```

`LEAVE.UNCLASSIFIED` имеет `NO_AUTOMATIC_EFFECT`: это подтверждённый, но не реклассифицированный факт, который не создаёт, не меняет, не закрывает и не вычисляет фактический период отпуска. Для него запрещены автоматическое изменение кадрового snapshot, period payload, `source_event_id` и применение как источника другого отпускного события. До ручной реклассификации он не заменяет документный draft и не участвует в отпускной цепочке. Для периодных канонических событий metadata будущего доменного контракта должна содержать нормализованные даты и основание; состав metadata будет определён отдельным implementation design.

## 7. Связь с исходным событием

Будущее nullable-поле `source_event_id` ссылается **только на корневой** `LEAVE.<leave_kind>.GRANT` в `employee_events.event_id`. Для `POSTPONE`, `EXTEND`, `RECALL`, `EARLY_RETURN` оно обязательно; оно никогда не ссылается на промежуточное изменение. Поэтому для одной отпускной цепочки все изменения имеют одинаковый `source_event_id`. Отдельный `predecessor_event_id` в v1.1 не вводится: непосредственный предшественник детерминированно определяется из действующих событий той же цепочки по `(effective_date, event_id)`.

Инварианты: source не равен собственному `event_id`; source и derived-event принадлежат одному `employee_id`; source существует, имеет тот же `leave_kind`, имеет код `GRANT` и статус `APPROVED`; derived-event не может ссылаться на `LEAVE.UNCLASSIFIED`. Текущий фактический период получается replay действующих событий одной цепочки по `(effective_date, event_id)`; терминальный `RECALL`/`EARLY_RETURN` закрывает период согласно payload. Это read-model, а не отдельная физическая колонка периода.

Void — только прикладная транзакционная операция, **не** `ON DELETE CASCADE`; события никогда физически не удаляются. Детерминированное правило v1.1: void корневого `GRANT` отклоняется с `409`, если существует хотя бы одно производное событие со статусом `APPROVED`; void производного события отклоняется с `409`, если существует более позднее `APPROVED` производное событие этой же цепочки. Сначала должны быть voided зависимые события в обратном детерминированном порядке `(effective_date DESC, event_id DESC)`, затем запрошенное. При любом конфликте snapshot или невозможности rollback транзакция откатывается и void отклоняется.

## 8. Связь с приказами

Приказ может иметь несколько пунктов и создавать несколько событий. Каждое созданное через приказ событие обязательно сохраняет `order_id`, `order_item_id` и удобочитаемый `order_ref`; `order_item_id` определяет конкретный пункт. API журнала обязан возвращать все три поля.

Прямые операции без приказа остаются допустимым каналом, если registry разрешает их. Их источник должен быть явно различим через будущий `source_channel` (`ORDER` или `DIRECT`; конкретный состав enum уточняется в implementation design), а `order_id`/`order_item_id` для `DIRECT` — `NULL`.

## 9. Жизненный цикл и отмена

Выбранные канонические хранимые и API-статусы: `APPROVED` и `VOIDED`. `APPROVED` означает фактически применённое действующее событие; отдельный статус `APPLIED` не вводится и не является API-алиасом. История не удаляется.

Выбранное UI-поведение: **`VOIDED` скрываются по умолчанию**, а фильтр «Отменённые» позволяет показать их с явной меткой «Отменено» и причиной отмены. Их нельзя показывать как действующие факты. Любой будущий API default обязан исключать voided, если явно не запрошен lifecycle filter.

## 10. Совместимость и алиасы

Существующие коды сохраняются без переименования: `HIRE`, `TRANSFER`, `POSITION_CHANGE`, `RATE_CHANGE`, `CORRECTION`, `TERMINATION`, `EMPLOYEE_ENROLLED_FROM_IMPORT`. Это **действующие канонические коды**, разрешённые для новых записей в пределах правил registry и соответствующих writers; они не являются legacy-кодами и не являются алиасами отпусков.

Алиасы чтения registry: `ANNUAL_LEAVE → LEAVE.ANNUAL.GRANT`, `MATERNITY_LEAVE → LEAVE.MATERNITY.GRANT`, `UNPAID_LEAVE → LEAVE.UNPAID.GRANT`. Только эти три значения являются legacy-кодами данного решения: новые записи ими не создаются. Алиасы не дают права предполагать существование исторических строк: миграция данных требуется только после отдельной проверки фактических данных.

## 11. Единый реестр событий

Рассмотрены варианты:

1. **Реестр в коде.** Версионируется вместе с доменными правилами, типами, writers и контрактными тестами; не требует runtime CRUD и предотвращает изменение классификации без review.
2. **Справочник БД.** Удобен для администрируемых классификаторов, но потребует управления редактурой, версионирования, миграций справочника и защиты от изменения смысла уже записанных кодов.

Выбран **versioned registry в коде**. Для Corpsite это безопаснее: классификатор является доменным контрактом, текущий registry уже кодовый, а самостоятельный DB-справочник сейчас создал бы второй путь изменения правил. Версия — immutable manifest/release registry, а не значение строки события; опубликованный код неизменяем семантически. DB `CHECK` генерируется/сверяется из registry в миграционном процессе; backend validation, API payload и frontend filters получают список из одного published registry endpoint. Ручные независимые списки запрещены.

## 12. Изменения будущего DB-контракта

Будущая миграция должна: расширить `event_type` constraint действующими каноническими кодами, v1.1 и сохраняемыми legacy-кодами; добавить `source_event_id` FK self-reference без каскадного удаления; добавить отличимый источник (`source_channel`); сохранить lifecycle `APPROVED`/`VOIDED`; добавить индексы для `(employee_id, source_event_id)` и отпускной цепочки. Ограничения same-employee, root-GRANT, anti-cycle и допустимой пары типов реализуются сервисной транзакционной проверкой, поскольку обычный FK/`CHECK` не покрывает их полностью.

## 13. Изменения будущего API-контракта

`GET /directory/personnel-events` возвращает `event_type`, registry-derived category/labels/leave_kind/operation, `lifecycle_status` (`APPROVED`/`VOIDED`), `order_id`, `order_item_id`, `order_ref`, `source_event_id`, `source_channel`. Фильтры: category, final event code, leave kind, leave operation и lifecycle status. API registry публикует только разрешённые для UI значения с локализованными названиями и immutable registry version.

Команды создания валидируют final code, source-chain и source channel против registry. Приказный apply — единственная команда для кодов `order_only`; прямой writer отвергает их до записи.

## 14. Изменения будущего frontend-контракта

UI удаляет локальный массив типов. Фильтры получают значения из registry и поддерживают: категорию, конечный код, а при `LEAVE` — вид и операцию. Строка приказного события получает ссылку по `order_id`; `order_ref` остаётся отображаемым текстом. Для voided используется default-exclusion и явный фильтр/маркер из раздела 9.

## 15. Инварианты и запреты

- Workflow-состояния не являются `employee_events`.
- Приказное событие создаётся только при фактическом apply `SIGNED`/`REGISTERED` приказа.
- Один event имеет один final code, а его атрибуты выводятся только registry данной версии.
- Не допускаются несуществующие, legacy-write или order-only коды вне разрешённого writer.
- Derived leave-event обязан ссылаться на корневой `GRANT` того же leave kind и сотрудника; промежуточная ссылка запрещена.
- `LEAVE.UNCLASSIFIED` имеет `NO_AUTOMATIC_EFFECT` и не участвует в периоде или source chain до ручной реклассификации.
- `VOIDED` не участвует в вычислении действующего периода и не отображается как активный; никаких физических delete и DB cascade нет.
- Каждое order-created событие связано с конкретным order item.

## 16. План миграции по этапам

1. Утвердить immutable registry v1.1, правила эволюции кодов и mapping legacy/aliases; отдельно профилировать реальные исторические данные.
2. Подготовить DB migration: constraints, root-only `source_event_id` без DB cascade, source channel, индексы; lifecycle остаётся `APPROVED`/`VOIDED`.
3. Ввести backend registry validation, отпускные writers и безопасный order apply/void chain.
4. Расширить read API, добавить registry endpoint и lifecycle filters.
5. Перевести UI журнала на registry-driven filters, приказные ссылки и voided presentation.
6. Провести ограниченную миграцию только подтверждённых исторических отпускных строк; верифицировать данные, writers и rollback сценарии.
7. После периода совместимости запретить legacy-коды на запись, сохранив чтение алиасов.

## 17. Риски и открытые вопросы

- Требуется доменное решение по payload периодов, частичным отзывам и нескольким последовательным extension.
- Нужно определить полный перечень отпускных операций для maternity/childcare и правила смены leave kind.
- Нужна реализационная детализация rollback snapshot для уже принятого правила: void зависимостей только в обратном порядке, с детерминированным отказом при конфликте.
- Требуются политика локализации и владения registry, а также правила version upgrade.

## 18. Критерии готовности к реализации

Architecture Review утверждает immutable registry и все v1.1 коды, root-only source semantics, lifecycle `APPROVED`/`VOIDED`, order-only policy и void strategy. До реализации должны быть согласованы API schemas, DB migration design, idempotency/rollback сценарии, data-profile report и тестовые случаи для всех минимальных отпускных кодов.

## 19. Что не входит в решение

Не входят проектирование и реализация электронных заявлений, согласований, ЭП, календаря и расчёта отпусков, табеля, замещения и формы приказа. Их интеграция ограничивается передачей основания/данных для фактического apply события.
