# ADR-061 — Каноническое фото Person и политика удаления тестовых кадровых обращений

- **Статус:** Accepted
- **Дата:** 26.07.2026
- **Размещение:** `docs/adr/ADR-061-canonical-person-photo-and-test-application-deletion-policy.md`
- **Связанные решения:** ADR-047 (Personal File), ADR-048 (Person ownership и запрет hard-delete Person), модель Personnel Application, PIF-PHOTO

## 1. Контекст

В реестре `/directory/personnel/lk` строка типа «Претендент» представляет не отдельный
агрегат Applicant, а Person с активным `PersonnelApplication`.

Кадровое обращение является эпизодом кадровой истории. Оно может завершиться приёмом,
отказом, отзывом или отменой, однако его штатный жизненный цикл не предполагает физическое
удаление. В локальной и опытной эксплуатации накопились тестовые обращения, которые
системному администратору необходимо безопасно очищать, не создавая общего механизма
удаления реальной кадровой истории.

Одновременно обнаружено, что фотография из электронной анкеты пока привязана только к
обращению:

- идентификатор хранится в `personnel_intake_drafts.payload.personal.photo_file_id`;
- файл хранится по пути
  `{PERSONNEL_PHOTO_STORAGE_ROOT}/{application_id}/{photo_file_id}.jpg`;
- каноническая карточка Person/PPR собственного файлового объекта фотографии не имеет;
- перенос сведений анкеты в PPR не делает фотографию канонической;
- удаление каталога обращения может уничтожить единственный экземпляр фотографии уже
  принятого человека.

Существующие поля `application_source`, `hr_note` и `idempotency_key` не позволяют
безошибочно отличить тестовые обращения от реальных. Следовательно, автоматическое
определение «тестовости» по имени, статусу, дате, источнику или тексту примечания запрещено.

## 2. Решение

Принимаются два связанных, но независимо реализуемых решения:

1. Фотография постоянной личной карточки принадлежит Person/PPR, а не кадровому обращению.
2. Кадровые обращения хранятся как история; hard-delete разрешается только для явно
   классифицированных тестовых обращений и только через отдельную административную
   операцию с серверными блокировками и независимым аудитом.

Реализация выполняется последовательно: сначала каноническое фото Person, затем
классификация и удаление тестовых обращений.

## 3. Каноническое фото Person

### 3.1. Владение и источник истины

Каноническое фото является person-scoped объектом:

- стабильная связь хранится по `person_id`;
- метаданные файла хранятся в БД;
- JPEG может храниться вне БД в постоянном файловом хранилище;
- путь не содержит ФИО, ИИН и другие персональные атрибуты;
- `photo_file_id` внутри intake payload не является канонической ссылкой Person.

Физическая модель (`files` + `persons.photo_file_id`, отдельная `person_photos` либо
эквивалентная типизированная модель) определяется рабочим пакетом. Независимо от выбранной
схемы должны выполняться следующие инварианты:

- файл имеет стабильный идентификатор, `person_id`, MIME type, размер и SHA-256;
- активное фото Person однозначно определяется;
- замена фото не переписывает аудиторскую историю;
- удаление или очистка обращения не удаляет канонический файл Person;
- доступ к байтам выполняется только через авторизованный API;
- резервное копирование БД и файлового хранилища рассматривается как единая операция.

### 3.2. Роль фото кадрового обращения

Фото, загруженное по intake-ссылке, является временным материалом обращения до кадрового
принятия. При принятии фото в постоянную карточку система:

1. валидирует файл штатными правилами Personnel Intake;
2. копирует байты в person-scoped хранилище;
3. создаёт канонические метаданные и связь с `person_id`;
4. проверяет SHA-256 и доступность новой копии;
5. только после успешной транзакции/компенсации делает фото активным в Person/PPR.

Копирование предпочтительнее перемещения: исходный материал обращения сохраняется на срок,
заданный политикой intake, а постоянная карточка не зависит от каталога `application_id`.

Канонизация выполняется по явному кадровому действию принятия фото. Для успешного HIRE Apply
она должна быть завершена не позднее завершения кадрового обращения, если в анкете имеется
допустимое фото. Неуспешная канонизация блокирует уничтожение исходного файла, но не должна
незаметно терять фотографию.

### 3.3. Переход для существующих фотографий

До включения удаления обращений выполняется backfill:

- найти intake payload с `personal.photo_file_id`;
- проверить существование и checksum файла;
- определить `person_id` через `PersonnelApplication`;
- не создавать дубликат, если тот же файл уже канонизирован;
- неоднозначные случаи направить на ручное решение;
- сформировать отчёт: перенесено, уже перенесено, файл отсутствует, требуется решение.

До успешного backfill конкретного обращения его фото-каталог считается защищённым от
физического удаления.

## 4. Политика кадровых обращений

### 4.1. Историчность по умолчанию

Каждое существующее и новое кадровое обращение по умолчанию считается реальным историческим
объектом. Терминальные состояния (`completed`, `withdrawn`, `cancelled`,
`resolution_rejected`) не являются основанием для hard-delete.

Для реальных обращений допустимы только штатные переходы жизненного цикла и архивное
представление. Кнопка удаления не заменяет отмену, отзыв, отказ или закрытие обращения.

### 4.2. Явная классификация тестовых данных

Вводится типизированная классификация обращения:

- `REAL` — реальное обращение; значение по умолчанию для всех существующих и новых записей;
- `TEST` — заведомо тестовые данные, созданные для разработки, обучения или проверки.

Запрещено автоматически присваивать `TEST` по ФИО, статусу, дате, источнику, примечанию,
окружению или другим косвенным признакам.

Пометить обращение как `TEST` может только канонический системный администратор. Обязательны:

- явное подтверждение;
- текстовая причина;
- неизменяемая запись независимого security audit;
- идентификаторы обращения, Person и администратора;
- предыдущее и новое значение классификации.

Изменение классификации не удаляет данные и является отдельным действием.

### 4.3. Условия hard-delete

Hard-delete доступен только каноническому системному администратору и только когда backend
одновременно подтвердил:

- `data_classification = TEST`;
- отсутствует связанный кадровый приказ;
- отсутствует созданный по обращению Employee/HIRE event/onboarding;
- сведения обращения не были перенесены в канонические разделы PPR либо все такие связи
  доказуемо отсутствуют;
- фото обращения отсутствует, уже канонизировано в независимое person-scoped хранилище либо
  явно признано ненужным тестовым файлом;
- нет других зависимостей, которые должны сохраняться как кадровая или юридически значимая
  история.

Проверка выполняется на сервере непосредственно внутри операции удаления. Скрытие кнопки в
UI не является контролем безопасности.

Если хотя бы одно условие не выполнено, операция возвращает отказ с конкретным кодом и
понятным сообщением. Обход блокировок флагом `force` не предусматривается.

### 4.4. Граница удаления

Операция удаляет только агрегат конкретного тестового `PersonnelApplication` и данные,
которые доказуемо принадлежат исключительно этому обращению. Точный dependency plan
формируется сервисом до изменения данных и исполняется в одной DB-транзакции с
компенсационным управлением файловой операцией.

Не удаляются:

- `Person`;
- канонические разделы PPR;
- каноническое фото Person;
- прежние или действующие Employee;
- кадровые приказы и события;
- независимая запись security audit.

Если после удаления остаётся Person/PPR shell без кадровых сведений и без активного
обращения, он не удаляется в рамках этой операции. Отдельная очистка целого тестового
Person-контура требует самостоятельного архитектурного решения и не входит в ADR-061.

### 4.5. Файловая атомарность

БД и файловая система не образуют общую ACID-транзакцию. Поэтому сервис не должен сначала
безвозвратно удалять файл, а затем пытаться удалить строки БД.

Допустимый шаблон:

1. построить и зафиксировать dependency plan;
2. переместить application-scoped файлы в закрытый quarantine/trash;
3. выполнить DB-транзакцию;
4. после commit удалить quarantined файлы асинхронно или по retention;
5. при rollback восстановить файлы.

Точный механизм может отличаться, но потеря файла при откате БД запрещена.

## 5. API, UI и аудит

### 5.1. API

Операции классификации и удаления разделяются. Их точные URL определяет рабочий пакет, но
контракт должен поддерживать:

- optimistic/concurrency guard;
- обязательную причину;
- предварительный dependency preview;
- стабильные коды блокировок;
- повторный серверный guard перед delete;
- идемпотентное представление результата.

### 5.2. UI

В `/directory/personnel/lk`:

- действие доступно только каноническому системному администратору;
- у реального претендента показывается не активная кнопка hard-delete, а объяснение, что
  обращение является кадровой историей;
- для удаления сначала выполняется отдельная маркировка `TEST`;
- подтверждение удаления показывает ФИО, `application_id`, причину и dependency summary;
- после успеха строка исчезает из реестра без затрагивания Person/PPR;
- при отказе строка остаётся, а пользователь видит конкретную блокировку.

Обязательный текст предупреждения:

> Физическое удаление допускается только для тестовых данных. Реальные кадровые обращения
> являются частью кадровой истории и должны сохраняться в архиве.

### 5.3. Независимый аудит

Минимальные события:

- `PERSONNEL_APPLICATION_CLASSIFIED_TEST`;
- `PERSONNEL_APPLICATION_CLASSIFICATION_REVERTED`;
- `PERSONNEL_APPLICATION_HARD_DELETED`.

Событие hard-delete хранится вне удаляемого агрегата и включает:

- `application_id`, `person_id`;
- ФИО-снимок для административного расследования;
- администратора, время и причину;
- классификацию;
- блокирующий/dependency snapshot и количества удалённых записей;
- результат файловой очистки;
- correlation/command id.

Аудит не должен содержать токены intake, байты фото или полный payload анкеты.

## 6. Инварианты

| Код | Инвариант |
|---|---|
| INV-061-01 | Каноническое фото принадлежит Person/PPR, не Personnel Application |
| INV-061-02 | Удаление обращения не удаляет Person, PPR или каноническое фото |
| INV-061-03 | Все существующие обращения мигрируются как `REAL` |
| INV-061-04 | `TEST` назначается только явно сисадмином, с причиной и аудитом |
| INV-061-05 | Реальное обращение физически не удаляется |
| INV-061-06 | Наличие приказа, Apply/HIRE/onboarding или переноса в PPR блокирует delete |
| INV-061-07 | UI не является границей авторизации; все правила повторяются backend |
| INV-061-08 | Файлы обращения не удаляются до успешной канонизации/разрешения фото |
| INV-061-09 | Security audit переживает удаляемый агрегат |
| INV-061-10 | ADR-061 не разрешает hard-delete Person |

## 7. Этапы реализации и распределение

### WP-ADR061-001 — Каноническое фото Person

Исполнитель: Cursor. Архитектурный review и приёмка: ChatGPT/Codex + пользователь.

Состав: схема и миграция, person-scoped storage/API, принятие intake-фото, backfill,
защита старых каталогов, backend/contract tests. Изменения удаления обращений не входят.

### WP-ADR061-002 — Управляемое удаление тестовых обращений

Исполнитель: Cursor только после приёмки WP-ADR061-001. Архитектурный review и приёмка:
ChatGPT/Codex + пользователь.

Состав: классификация `REAL/TEST`, независимый аудит, dependency preview, backend hard-delete
service, файловый quarantine/compensation, кнопка и предупреждение в `/directory/personnel/lk`,
backend/frontend/security tests.

Не объединять WP-ADR061-001 и WP-ADR061-002 в один commit или deploy.

## 8. Последствия

Положительные:

- фото переживает завершение и очистку временного обращения;
- реальная кадровая история защищена от случайного удаления;
- тестовые данные можно очищать контролируемо и аудируемо;
- границы Person, PPR и Personnel Application остаются явными.

Издержки:

- требуется новая файловая модель и backfill;
- файловые операции требуют quarantine/compensation;
- накопленные тестовые обращения нельзя массово определить автоматически;
- обращения с уже перенесёнными данными потребуют отдельного разбора.

## 9. Не входит в решение

- hard-delete Person или PPR;
- массовое автоматическое распознавание тестовых данных;
- удаление реальных завершённых обращений;
- универсальная очистка всех данных тестового человека;
- хранение JPEG непосредственно в БД;
- окончательный срок хранения исходных intake-файлов — он задаётся отдельной retention
  политикой.

## 10. Критерии принятия ADR

ADR переводится из `Proposed` в `Accepted` после подтверждения пользователем:

1. фото является постоянным person-scoped объектом;
2. реальные кадровые обращения сохраняются как история;
3. hard-delete возможен только после явной маркировки `TEST`;
4. Person/PPR и канонические сведения не удаляются этой операцией;
5. реализация разделена на два последовательных рабочих пакета.
