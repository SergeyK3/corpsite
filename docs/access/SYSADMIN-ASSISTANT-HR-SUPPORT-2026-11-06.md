# Кадровая поддержка SYSADMIN_ASSISTANT — локальный первый этап

Дата: 2026-11-06. Реализация локальная, без коммита, push и деплоя.

## Проверенная среда и исходное сравнение

Перед изменениями и запуском API запрос `SELECT current_database()` подтвердил
`corpsite_test` на локальном PostgreSQL `127.0.0.1:5432`.
В `.env` исходно указана `corpsite`; файл не менялся. Все подключения для
миграций, тестов и просмотра явно направлены в `corpsite_test`.

Исходная ревизия тестовой БД: `asst001`.
У существующего помощника `kabi.a` не было `employee_id`.
Его персональные назначения: `DOCUMENTATION_READ` и четыре
`ASSISTANT_PERSONNEL_ORDERS_*` для подготовки, регистрации, применения и
удаления собственных черновиков. Назначений на уровне роли помощника не было.

Для `HR_HEAD` в БД обнаружены активные ROLE-назначения:
`HR_ENROLLMENT_MANAGER`, `CONTROL_LIST_EXPORT`, `PPR_MIGRATION_STATUS_READ`,
четыре `PPR_STAGE0…3_*`, `VIEW_TRAINING_CERTIFICATE_DETAILS`,
`INCOMING_INFO_READ`, `INCOMING_INFO_REGISTER`, а также согласование и чтение
аудита удаления тестовых кадровых данных. Последняя группа помощнику не выдаётся.
Исправление карточек в коде дополнительно требует `PERSONNEL_CARD_EDIT` либо
административного доступа; одно название `HR_HEAD` это право не заменяет.

В коде этапы переноса дополнительно требовали точную роль `HR_HEAD`.
Общий фильтр самостоятельных профилей блокировал кадровые изменения вне
перечня операций с приказами и все Excel-маршруты. В интерфейсе кадровые формы
за пределами приказов перехватывались режимом просмотра.

## Реализация

Помощнику не назначаются `HR_HEAD`, `ADMIN`, `SYSTEM_ADMIN`, `SYSADMIN_CABINET`,
`ACCESS_ADMIN`, `USER_ACCESS_ADMIN` или `HR_ENROLLMENT_MANAGER`.
Профиль получает собственные USER-разрешения; административные полномочия
и управление правами остаются выключенными.

Новые кадровые разрешения:

- `ASSISTANT_HR_SUPPORT`;
- `ASSISTANT_PERSONNEL_CARD_EDIT`;
- `ASSISTANT_HR_EXPORT`;
- `ASSISTANT_PPR_STAGE0_MANAGE` … `ASSISTANT_PPR_STAGE3_MANAGE`;
- `ASSISTANT_PERSONNEL_ORDERS_VOID`.

Внутри профиля также явно назначаются существующие узкие разрешения:
`CONTROL_LIST_EXPORT`, `PPR_MIGRATION_STATUS_READ`,
`VIEW_TRAINING_CERTIFICATE_DETAILS`, `PERSONNEL_ORDERS_CANCEL_OWN`,
`PERSONNEL_ORDERS_CANCEL_SCOPE`, `PERSONNEL_ORDERS_ARCHIVE`,
`PERSONNEL_ORDERS_RESTORE`. Новые аккаунты получают тот же набор через
действующий сервис создания самостоятельных профилей.

Все дополнительные маршруты перечислены точно в
`app/security/sysadmin_assistant_hr_routes.py`; разрешения по префиксу URL нет.
Каждая операция использует личный идентификатор помощника. Кадровые изменения
проходят прежние сервисы; аудит транзакции помощника сохраняется атомарно с
изменениями. Транзакции PREVIEW с `READ ONLY` не пытаются записывать аудит
изменения; записываемые этапы и принятие аудируются.

Миграции, применённые только к тестовой БД:

- `asst002`: разрешения и персональные назначения кадровой поддержки;
- `asst003`: отсутствовавший домен аудита `contacts` — необходим для уже
  существующего API исправления контактов;
- `asst004`: отдельные разрешения недеструктивного жизненного цикла приказов.

При реальном принятии обучения выявлена ошибка существующего построителя
аудита: `Decimal` количества часов не сериализовался в JSON. Теперь он
сохраняется точной десятичной строкой; есть отдельный регрессионный тест.

## Проверки

Серверные проверки выполняются с ранним pytest DB guard и исключительно
`TEST_DATABASE_URL`, указывающим на `corpsite_test`.

Итог профильного набора: **139 серверных тестов прошли**. Интерфейс:
**60 тестов прошли**; TypeScript прикладного кода — без ошибок.

- Профильные серверные проверки: настоящий вход без сотрудника, смена временного
  пароля, исправление контактов, отказ некорректных данных, создание и применение
  приказа, отказ повторного применения, архивирование/восстановление, реальное
  авторство удаления, все четыре этапа переноса до `ACCEPTED`, точный аудит.
- Проверены прямые запреты на справочники, оргструктуру, настройки, шаблоны,
  пользователей, пароли, права и исключительное удаление.
- Проверены сохранение поведения `HR_HEAD` и ограничений `DOCUMENTATION_VIEWER`.
- Проверки UI: навигация, выдача возможностей, описание профиля, четыре панели
  переноса и режим просмотра справочников.
- TypeScript прикладного кода проверяется отдельно от существующих тестовых
  файлов: общий `tsc` репозитория содержит прежние ошибки типов в тестах.
- Браузерная проверка: только `http://127.0.0.1:3000`, настоящий API на `8000`.
  Вход, программа переноса, карточка, отключённые кнопки изменения должностей и
  настоящее скачивание `Должности.xlsx`; ошибок JavaScript не обнаружено.
  `404` фото тестового сотрудника означает отсутствие фотографии.

Дополнительный старый набор `test_adr043_phase_c4_1_lifecycle_api.py` имеет
7 ошибок подготовки данных: его фикстуры не заполняют обязательное поле
`hr_import_batches.import_code`. Схема БД и эти старые фикстуры не менялись.

Проверены также реальные вызовы трёх дополнительных Excel-маршрутов:

| Выгрузка | Результат на текущих данных corpsite_test |
|---|---|
| Контрольный список | `409 CONTROL_LIST_ASSIGNMENT_CONFLICT`: нарушен инвариант основного назначения у части сотрудников; отказ сохранён, данные не исправлялись автоматически |
| Канонический снимок | `404`: нет активного снимка `HR_CONTROL_LIST` |
| Кадровые изменения | Прежний `500`: старый экспорт обращается к `hr_canonical_snapshots.version`, отсутствующему в текущей схеме снимков |

Это ограничения данных/старых экспортов, а не отсутствие разрешений помощника.
Успешная выгрузка этих трёх книг в данной БД не подтверждена. Создание снимка,
исправление назначений и согласование старого экспорта с новой схемой не
выполнялись в рамках изменения профиля доступа.

## Ручная проверка и оставшиеся границы

Открыть `http://127.0.0.1:3000/login`.
Тестовый аккаунт помощника: изолированный тестовый помощник, без employee_id.
Для сравнения создан изолированный тестовый просмотрщик. Учётные данные в релиз не включаются.
Существующий `kabi.a` также получил дополнительные назначения в **тестовой** БД;
его пароль не менялся.

API запускается локальным `.tmp/assistant_preview_api.py`, который перед запуском
проверяет фактическое имя БД и принудительно использует `corpsite_test`.
Для ручного просмотра только в этом процессе включены существующие feature flags
Stage 3 и PPR bridge; `.env`, рабочая БД и сервер не изменяются.

Не расширяется общий административный контроллер массового кадрового жизненного
цикла, overrides и операций идентификации/привязки пользователей. Автоматическая
проверка отклонила такое общее расширение как недостаточно ограниченное по объёму.
Сохранён явный список операций первого этапа. Для расширения этого отдельного
административного блока нужно согласовать конкретные действия и разрешения.

Существующие ограничения самих документов, шаблонов, отсутствующих данных и
реализованных редакторов карточки сохраняются. Новые редакторы разделов,
которых ещё нет у HR_HEAD, в этом этапе не добавляются. В тестовой БД оставлены
созданные проверками кадровые записи и аудит; служебные pytest-аккаунты отключены.
