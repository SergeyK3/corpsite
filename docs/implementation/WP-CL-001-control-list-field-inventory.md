## 1. Цель и границы

Цель `WP-CL-001` — проверить фактические источники данных активного персонала и зафиксировать матрицу для будущего Excel-экспорта контрольного списка. Источником истины остаются канонические сущности Person/Employee, назначения, оргструктура и профильные записи PPR. Импортные строки, intake-анкеты, снимки и будущий Excel-файл источниками истины не являются.

Выполнено только чтение моделей, миграций, сервисов, API-схем, импортов, действующих Excel-экспортов, ADR/WP-документации и агрегатов локальной БД. Код продукта, схема и данные БД не изменялись; экспорт, API, UI, миграции и тесты продукта не создавались.

В границы инвентаризации входят:

- точное воспроизводимое определение текущего активного персонала;
- проверка каждого поля исходного контрольного списка и дополнительных канонических полей;
- сопоставление будущей экспортной и существующей импортной схем;
- правила форматов, множественных значений, сортировки, назначения и защиты ПДн;
- перечень пробелов и решений, необходимых до контракта проекции `WP-CL-002`.

Не входят: утверждение кадровой семантики владельцем продукта, исправление или заполнение данных, перенос legacy/import/intake-значений в канон и любая продуктовая реализация.

## 2. Проверенные источники

### 2.1. Каноническая модель и read-модель

| Область | Фактический источник | Существенное наблюдение |
| --- | --- | --- |
| Личность | `persons` (`person_id`, `full_name`, компоненты имени, `birth_date`, `iin`, `person_status`) | `iin` ограничен 12 цифрами; отдельные поля имени в текущих данных не заполнены, поэтому рабочий источник ФИО — `full_name`. |
| Операционный сотрудник | `employees` (`employee_id`, `person_id`, `operational_status`, `is_active`, `date_from`, `date_to`) | Это контекст занятости, а не самостоятельный источник биографических данных. |
| Назначение | `person_assignments` и `employee_assignment_links` | Есть тип занятости, ставка, период, `active_flag`, `is_primary` и lifecycle; модель допускает несколько назначений. |
| Оргструктура | `org_units`, `deps_group` | Подразделение связано с группой через `org_units.group_id`; почти все активные подразделения локальной БД имеют группу. |

| Контакты | `contacts` | Есть person-owned `phone`, но заполнение неполное и модель не задаёт типизированный набор «основной/дополнительный» для экспорта. |

Существующий отчёт «Личный состав» в `app/services/personnel_reports_service.py` уже строит общий preview/XLSX из операционных данных, но содержит только №, ФИО, должность и ставку. `hr_canonical_snapshot_export_service.py` выгружает импортный снимок; его payload не может стать источником будущего экспорта из личных карточек.

## 3. Определение включаемого персонала

### 3.1. Утверждённое определение для первой версии

Дата среза `T` — текущая календарная дата сервера в утверждённом часовом поясе организации `Asia/Almaty`. Значение `T` вычисляется один раз на сервере и применяется ко всей выборке. Исторические выгрузки и произвольная дата среза в MVP не входят: `person_status`, `operational_status` и `active_flag` отражают текущее состояние, а не полную бивременную историю.

Сотрудник включается в основной лист ровно один раз, если одновременно выполняются условия:

1. `employees.person_id` ссылается на существующий `persons.person_id`.
2. `persons.person_status = 'active'`.
3. `employees.operational_status = 'active'` и `coalesce(employees.is_active, true) = true`.
4. Период Employee содержит `T`: `date_from IS NULL OR date_from <= T`; `date_to IS NULL OR date_to >= T`.
5. Есть ровно одно основное назначение того же `person_id`, удовлетворяющее одновременно: `active_flag = true`, `is_primary = true`, `lifecycle_status = 'active'`, `start_date <= T`, `end_date IS NULL OR end_date >= T`. `employee_assignment_links` сохраняет происхождение связи, но действующий roster выбирает назначение по `person_id`, поэтому наличие строки link не является критерием включения.
6. Подразделение назначения входит в организационный scope пользователя, запускающего экспорт.

Пограничные даты включаются. Кандидаты, `draft`, `suspended`, `terminated`, неактивные/merged лица, закрытые или будущие назначения исключаются. Если найден хотя бы один сотрудник, который проходит условия Person/Employee, но не имеет ровно одного активного основного назначения на `T`, файл не формируется.

### 3.2. Несколько назначений и совместительство

Модель допускает `primary`, `part_time`, `internal_combo`, `external` и `locum`. Наличие нескольких параллельных назначений само по себе допустимо, однако правило канонического плана «одна строка — один активный сотрудник» требует одного выбранного основного назначения.

- Основной лист не дублирует сотрудника по вторичным назначениям.
- При ровно одном основном назначении оно определяет подразделение, должность, категорию, ставку и дату начала основной работы.
- При двух и более основных назначениях экспорт не выбирает строку через `ROW_NUMBER()`: это ошибка инварианта.
- При отсутствии активного основного назначения либо при их множественности формирование прекращается, пользователю возвращается агрегированная диагностика, неоднозначное назначение автоматически не выбирается и неполный файл не создаётся.
- Дополнительные и вторичные назначения не создают отдельные строки и в первой версии не экспортируются. Возможность отдельного листа рассматривается только в следующих версиях.

Существующий roster-сервис также выбирает активное основное назначение на `CURRENT_DATE`, но при дубле берёт первую строку по `assignment_id`. Это поведение нельзя переносить в новый контракт. Отдельный путь карточки требует единственного активного назначения любого типа и при множественности возвращает 409; это тоже не является готовой политикой совместительства.

## 4. Статусы готовности

| Статус | Значение в этой инвентаризации |
| --- | --- |
| `READY` | Канонический источник и однозначное правило уже доступны для целевой выборки. |
| `DERIVED` | Значение воспроизводимо вычисляется из канонических данных по зафиксированному правилу. |
| `PARTIAL` | Источник существует, но покрытие неполное, данные не верифицированы либо read-модель переходная. |
| `MISSING` | Допустимого канонического источника в системе нет. Import/intake raw не устраняет этот статус. |
| `DECISION_REQUIRED` | Реализация зависит от неутверждённой бизнес-семантики или структуры файла. |

### 5.1. Метаданные файла, не являющиеся строковыми полями

Файл содержит отдельный лист `Метаданные`: версия схемы, дата среза `T`, время формирования, часовой пояс `Asia/Almaty`, организационный scope, применённые фильтры и инициатор экспорта. Эти значения не повторяются в строках основного листа. `WP-CL-002` определяет технические имена и типы полей контракта, не меняя утверждённый состав.

## 6. Правила представления данных

### 6.1. Даты и актуальность

- Все кадровые даты в ячейках записываются как даты Excel, не как локализованные строки; отображение — `ДД.ММ.ГГГГ`.
- Год окончания образования — четырёхзначный год, полученный из `completed_at`; если известна полная дата, исходная точность не теряется в канонической проекции.
- Все фильтры активности и расчёты используют одно значение `T`; запрещено вызывать `CURRENT_DATE` независимо для разных частей одного экспорта.
- MVP разрешает только текущий срез в `Asia/Almaty`. Исторический `T` не поддерживается.

### 6.2. ИИН и телефоны

- ИИН экспортируется только как текст из 12 цифр. Excel не должен удалять ведущие нули, применять экспоненциальную запись или числовое форматирование.
- Телефоны экспортируются как текст. Нормализованная форма сравнения должна сохранять знак страны и цифры; отображаемая форма и допустимость добавочных номеров требуют контракта.
- Пустой, невалидный или недоступный по правам ИИН/телефон не заменяется нулями, маской как значением данных или строкой `нет`; ячейка остаётся пустой. Маска допустима только как UI-представление, не как ложное значение экспортной проекции.

### 6.3. ФИО и пустые значения

- Канонический порядок: `Фамилия Имя Отчество`; отсутствующее отчество опускается без двойных пробелов.
- Пока компоненты имени не заполнены, используется `persons.full_name` после trim и схлопывания повторных пробелов. Парсить строку обратно на компоненты нельзя.
- SQL `NULL`, отсутствующая запись и пустая строка дают пустую ячейку. Значения `0`, `не указано` и `нет` не синтезируются.
- Различие «данных нет», «доступ запрещён» и «не применимо» должно сохраняться в API/диагностике, даже если пользовательская ячейка одинакова и пуста.

### 6.4. Множественные образования, обучения, степени, награды и телефоны

В первой версии отдельные нормализованные листы не создаются. Несколько значений помещаются в соответствующую ячейку основного листа через перевод строки (`LF`) с включённым переносом текста в Excel.

- Образования сортируются по `completed_at` по возрастанию (`NULL` после датированных), затем по `started_at`, нормализованному `institution_name` и `education_id`. Каждая запись получает порядковый префикс `[1]`, `[2]` и далее. Один и тот же индекс и порядок используются в колонках «Образование», «Год окончания» и «Специальность по диплому»; отсутствующий компонент оставляет проиндексированную пустую позицию. Поэтому учебное заведение, год и специальность одного диплома логически не разрываются.
- Повышения квалификации сортируются по `completed_at` по убыванию (`NULL` после датированных), затем по `started_at` по убыванию, нормализованному `title` и `training_id`.
- Учёные степени и награды сохраняют порядок элементов утверждённой канонической проекции массива; индекс массива служит стабильным последним ключом. Import/intake fallback не добавляется.
- Телефоны дедублируются по нормализованному номеру без изменения канонических записей, затем сортируются лексикографически по нормализованному номеру и `contact_id`.
- Составные части одной записи соединяются ` — `; разные записи разделяются переводом строки. Значения не обрезаются молча: поведение при превышении лимита ячейки Excel должно быть определено техническим контрактом `WP-CL-002`.

### 6.5. Стабильный порядок строк

Порядок основной таблицы: нормализованное имя группы подразделений → имя подразделения → нормализованное ФИО → `employee_id`, все по возрастанию с явно заданной collation/нормализацией. Пустая группа располагается после непустых. Номер присваивается после сортировки.

Текущий roster дополнительно сортирует по рангу должности. Новый контракт не должен неявно наследовать этот ранг, потому что канонический план фиксирует порядок «группа → подразделение → ФИО → employee_id».

## 7. Сопоставление с импортной схемой

Текущий `scripts/import_hr_control_list.py` нормализует поля `full_name`, `iin`, `birth_date`, `sex`, `nationality`, `department`, `position_raw`, `education_raw`, `diploma_specialty_raw`, `qualification_raw`, `experience_raw`, `training_raw`, `education_training_raw`, `certification_raw`, `degree_raw`, `awards_raw`, `note_raw`, `phone_raw`, `source_sheet`, `source_row_number`. Разные типы листов содержат разные подмножества; тип занятости выводится из имени/класса листа, а не из канонического назначения.

| Сопоставление | Поля | Вывод |
| --- | --- | --- |
| Совпадают по бизнес-понятию и имеют канонический источник | ФИО, дата рождения, ИИН, подразделение, должность, образование, специальность, обучение, степень, награды, телефон | Совпадение названия не разрешает читать import row; экспорт читает только канон. Для последних пяти покрытие частичное/переходное. |
| Совпадают только концептуально, канонического источника нет | пол, национальность, квалификационная категория, примечание | Эти колонки нельзя заполнить из raw staging как официальные сведения. |
| Отличаются по семантике | `positions.category` против `qualification_raw`/`certification_raw`; группа подразделений против legacy секции/листа; дата назначения против raw-стажа | Нужны отдельные колонки и термины; объединение запрещено. |
| Импортные поля, которые не экспортируются | `source_sheet`, `source_row_number`, raw-композиты, тип/класс листа, match/review/diff status, ошибки, profile override, hashes, `match_key`, служебные IDs staging/snapshot | Это provenance и состояние ETL, не кадровые сведения сотрудника. Декларационные/служебные листы также не входят в персональный экспорт. |
| Дополнения экспортной схемы | каноническая группа подразделений, категория должности, ставка, дата начала основного назначения, `employee_id`, `schema_version`, дата среза, параметры и инициатор | Их нет либо они неустойчивы в исходной широкой таблице, но они нужны для контроля и воспроизводимости. |

Импортный слой содержит исторически больше непустых raw-значений (например, пол, национальность, стаж, квалификация), чем канонический профиль. Это показатель необходимости верифицированного переноса/дозаполнения, а не разрешение использовать staging как fallback будущего экспорта.

## 8. Защита персональных данных и права

- Экспорт с ИИН, телефонами, национальностью и иными чувствительными сведениями — отдельное привилегированное действие, а не следствие обычного права видеть список сотрудников.
- Действующая PPR read-модель показывает полный ИИН только org-wide/привилегированному кадровому читателю; иначе возвращает маску. Экспорт должен иметь не менее строгий отдельный permission и учитывать org scope.
- Для массового Excel-экспорта вводится отдельное серверное permission. Экспорт разрешён только уполномоченным кадровым ролям в пределах их организационного scope; полный ИИН и телефоны доступны только при наличии этого permission. Точное имя permission предлагает `WP-CL-002` по действующим соглашениям проекта.
- Каждый экспорт аудируется: инициатор, время, scope, фильтры, дата среза, число строк и результат операции. Содержимое ИИН/телефонов не записывается в application logs.
- Ошибки и диагностика не должны содержать значения ИИН и телефонов. Временные файлы должны иметь ограниченный срок жизни и доступ, заданный позднейшим пакетом.
- Файл наследует риск утечки после скачивания: UI должен предупреждать о ПДн, а права должны проверяться сервером в момент формирования, не только при показе кнопки.
- Национальность требует отдельной проверки правового основания и минимизации данных до включения в схему.

## 9. Зафиксированные ограничения и вопросы WP-CL-002

### 9.1. Закрытые продуктовые решения и известные пробелы

Прежние вопросы `D-001`—`D-009` закрыты решениями, отражёнными в разделах 3, 5, 6, 8 и 10. Следующие пробелы не блокируют контракт первой версии, потому что соответствующие поля исключены либо явно допускают пустое значение:

| ID | Зафиксированное ограничение | Решение для MVP |
| --- | --- | --- |
| `G-001` | Нет canonical пола | Поле не экспортируется; raw import не используется |
| `G-002` | Нет canonical национальности | Поле не экспортируется; требуется отдельное правовое решение и typed canonical home |
| `G-003` | Нет typed home квалификационной/медицинской категории | Поле не экспортируется; дальнейшая модель следует ADR-060 |
| `G-004` | Нет политики и canonical home общего примечания | Поле не экспортируется |
| `G-005` | Образование и обучение заполнены частично, verified-покрытие отсутствует | Канонические значения экспортируются, отсутствие даёт пустую ячейку; intake/import fallback запрещён |
| `G-006` | Степени и награды представлены переходной канонической проекцией | Экспортируется только каноническая часть проекции; отсутствие даёт пустую ячейку |
| `G-007` | Телефоны заполнены частично | Канонические контакты экспортируются по утверждённому правилу; отсутствие даёт пустую ячейку |
| `G-008` | Одно активное подразделение локально не имеет группы | «Группа подразделений» остаётся пустой; искусственное значение «Без группы» не создаётся |

### 9.2. Открытые технические вопросы для WP-CL-002

Эти вопросы не меняют утверждённую бизнес-семантику и должны быть решены при проектировании read-only контракта:

1. Точное имя нового permission и его отображение на действующие кадровые роли по соглашениям проекта.
2. Имена, типы и версия полей API-проекции, включая представление метаданных и агрегированной диагностики назначения.
3. HTTP-статус и машинный формат ошибки при отсутствии или множественности основного назначения; ответ не должен раскрывать ПДн сверх scope пользователя.
4. Технический источник `Asia/Almaty` в конфигурации и гарантия однократного вычисления `T` на запрос.
5. Представление множественных полей в проекции: типизированные массивы должны сохранять связь и порядок, а преобразование в строки Excel остаётся ответственностью следующего пакета.

Механизм записи аудита экспорта и поведение при достижении лимита Excel-ячейки уже заданы как обязательные ограничения, но проектируются в пакете Excel-экспорта, а не меняют контракт `WP-CL-002`: аудит обязан фиксировать успешный или неуспешный результат, а молчаливое обрезание значения запрещено.

## 10. Утверждённая схема MVP

Первая версия должна быть пригодна для работы отдела кадров и включает все доступные канонические сведения, в том числе частично заполненные. Основной лист `Контрольный список` содержит ровно следующие колонки в указанном порядке:

| № | Заголовок | Поле проекции | Правило MVP |
| ---: | --- | --- | --- |
| 1 | № | `row_number` | Присваивается после итоговой сортировки |
| 2 | Группа подразделений | `org_group` | Канонический `deps_group`; допускается пустое значение |
| 3 | Подразделение | `org_unit` | Подразделение основного назначения |
| 4 | Фамилия, имя, отчество | `full_name` | Канонический порядок ФИО |
| 5 | Дата рождения | `birth_date` | Excel date; допускается пустое значение |
| 6 | ИИН | `iin` | Excel Text; допускается пустое значение; доступ только с export permission |
| 7 | Занимаемая должность | `position` | Должность основного назначения |
| 8 | Категория должности | `position_category` | Не квалификационная и не медицинская категория |
| 9 | Ставка | `employment_rate` | Числовое десятичное значение |
| 10 | Дата начала в должности | `assignment_start_date` | Excel date |
| 11 | Образование | `education` | Несколько значений через перевод строки, синхронно с колонками 12–13 |
| 12 | Год окончания | `education_graduation_year` | Несколько значений через перевод строки, синхронно с колонками 11 и 13 |
| 13 | Специальность по диплому | `diploma_specialty` | Несколько значений через перевод строки, синхронно с колонками 11–12 |
| 14 | Повышение квалификации | `training` | Несколько значений через перевод строки |
| 15 | Учёная степень | `academic_degree` | Несколько значений через перевод строки |
| 16 | Награды | `awards` | Несколько значений через перевод строки |
| 17 | Телефоны | `phones` | Excel Text; несколько значений через перевод строки; доступ только с export permission |
| 18 | ID сотрудника | `employee_id` | Скрытая техническая колонка |

Порядок строк: `Группа подразделений → Подразделение → ФИО → employee_id`. Номер строки вычисляется после этой сортировки.

Отдельный лист `Метаданные` содержит:

- версию схемы;
- дату среза;
- время формирования;
- часовой пояс `Asia/Almaty`;
- организационный scope;
- применённые фильтры;
- инициатора экспорта.

Отдельные листы для образования, обучения, наград и телефонов в MVP не создаются. Поля со статусом `PARTIAL` экспортируются с допустимыми пустыми значениями. Поля `MISSING` — пол, национальность, квалификационная категория и примечание — не экспортируются. Профессиональная группа персонала и стаж работы также не входят в MVP.

## 11. Итог WP-CL-001

1. Фактическая основа активной выборки зафиксирована: Person + активный Employee + ровно одно основное активное назначение на текущую дату в `Asia/Almaty` + оргструктура + должность.
2. Локальная контрольная выборка по этому правилу содержит 593 строки; это подтверждает техническую реализуемость утверждённой схемы, но не полноту всех кадровых полей.
3. Состав основного листа из 18 колонок, лист `Метаданные`, порядок строк, сериализация множественных значений, fail-closed правило назначения, scope и требования к ПДн определены.
4. `MISSING`: пол, национальность, квалификационная категория и примечание — исключены из MVP. Профессиональная группа персонала заменена группой подразделений. Стаж исключён; будущий официальный расчёт допускает только подтверждённые периоды с объединением пересечений на дату среза.
5. Открыты только технические вопросы раздела 9.2, не требующие изменения утверждённой продуктовой семантики.
6. `WP-CL-001` готов к рассмотрению и формальному завершению. После его принятия можно переходить к `WP-CL-002` и проектированию read-only контракта; до принятия реализация экспорта, миграций, API и UI остаётся запрещённой каноническим планом.
