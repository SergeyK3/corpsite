# План размещения JSON кадровых приказов

Статус: краткий план реализации. Сверка выполнена с
[`personnel-orders-json-storage-draft.md`](personnel-orders-json-storage-draft.md),
`app/db/models/personnel_orders.py` и действующими миграциями кадровых
приказов. Это не миграция и не проект новой подсистемы.

## Что уже можно использовать

| Потребность черновика | Имеющееся место хранения | Решение |
|---|---|---|
| Шапка: идентификатор, номер, дата, класс, статус, подписант | `personnel_orders` | Использовать без изменения. `order_number` и `order_date` уже допускают `NULL`. |
| Несколько `actions` одного приказа, в том числе без сотрудника | `personnel_order_items` | Один `action` — одна строка пункта; `employee_id` уже nullable, а `item_number` задаёт порядок. |
| Типозависимые данные и исходные формы ФИО | `personnel_order_items.payload JSONB` | Использовать без изменения: хранить здесь `data`, `basis_ids` и снимок `employee.name` с фактически найденными формами. Даты периода остаются в `effective_date`, `period_start`, `period_end`, без их дублирования в JSON. |
| Название приказа на kk/ru и текст | `personnel_order_localized_texts` | Использовать без изменения; это не следует дублировать в новом JSON-поле. |
| Файлы самого приказа, включая локальный путь | `personnel_order_attachments` и, для сформированных копий, `personnel_order_prints` | Использовать существующие ссылки. `SIGNED_SCAN` и `UNSIGNED_DRAFT` относятся к самому приказу; путь `file_path` уже поддержан. `BASIS_DOCUMENT` не подменяет файл приказа. |
| Связь приказа с записью входящей информации | `incoming_document_personnel_order_links` | Существующая связь с приказом сохраняется. |
| Действия после оформления | текущие жизненный цикл и `employee_events` | Не включать в JSON приказа: они уже отделены от реквизитов приказа. |

`personnel_order_item_bases` не покрывает модель из черновика: в ней ровно
одно основание на пункт (`UNIQUE(order_item_id)`), оно не может быть общим для
нескольких пунктов или приказов. Таблицу следует оставить для уже работающего
редакционного контура и обратной совместимости, но не использовать как
каноническое хранилище нового набора `basis_documents`.

## Где хранить JSON

Добавить **одно** поле `storage_json JSONB NOT NULL DEFAULT '{}'::jsonb` в
`personnel_orders`. Оно хранит только реквизиты черновика, которым нет
нормализованного места:

- `schema_version` и `requisites_status`;
- формы имени подписанта, если они извлечены из источника;
- `basis_documents` со стабильными `basis_id`, в том числе
  `incoming_record_ref` и допустимым `local_file_ref`.

Связь основания с пунктом хранится в уже существующем
`personnel_order_items.payload.basis_ids`. Один и тот же стабильный `basis_id`
может повторяться в JSON разных приказов; это логическая ссылка, не новая
глобальная таблица документов. Следовательно, импорт не должен считать такие
повторы разными основаниями только из-за нахождения в разных приказах.

Полный объект из черновика при чтении собирается из шапки, строк пунктов,
локализованных текстов, `storage_json` и файловых ссылок. Хранить его целиком
и параллельно дублировать шапку, `actions` или `source_files` в одном JSONB не
нужно.

## Минимальные изменения таблиц

1. Одно поле `personnel_orders.storage_json`, как описано выше.
2. Расширить существующие ограничения `order_type_code` и `item_type_code`
   кодами, которые будут разрешены к записи. В частности, подтверждённый
   `PERSON_NAME_CHANGE` сейчас отсутствует; существующие `HIRE`, `TRANSFER`,
   `TERMINATION`, начало/прекращение совмещения и два вида отпуска уже
   разрешены. Для сводного приказа сохраняется `COMPOSITE` в шапке, а типы
   принадлежат его пунктам.

Других таблиц, отдельных хранилищ файлов или таблицы оснований на этом этапе
не требуется. Если позднее понадобится единая физическая карточка одного
основания с гарантированной ссылочной целостностью между приказами, это будет
отдельное решение, а не неявное расширение данного плана.

## Совместимость с приказами и импортом

- Существующие колонки и их значения остаются источником для журнала,
  статусов, поиска, связей с сотрудником и `employee_events`. Новый JSON их
  не заменяет.
- Для старых приказов `storage_json = {}` означает «данных этого формата нет»,
  а не отсутствие или недействительность приказа. Обратное заполнение —
  только из проверенных источников; номер, дату, ФИО в падеже и основания не
  следует выводить по косвенным признакам.
- Текущий импорт ревью-записей приказов не создаёт `personnel_orders`;
  его формат и записи не изменяются. При последующем создании приказа из
  проверенной импортной записи старые поля записываются как прежде, а
  `storage_json` и `payload` заполняются только тем, что реально распознано.
- В коде в момент реализации потребуется синхронно расширить текущие
  белые списки и проверки типов (они есть не только в ограничениях БД), но
  это не требует изменения существующих записей или формата импорта.
