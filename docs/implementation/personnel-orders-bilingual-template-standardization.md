# Стандартизация двуязычных кадровых приказов

**Статус:** согласованная концепция для ближайшей реализации  
**Дата:** 2026-09-23

## 1. Цель

Формировать привычный текст кадрового приказа из одних структурированных
данных одновременно на казахском и русском языках. Это не перевод готового
текста: каждая языковая версия создаётся по своему утверждённому шаблону.

## 2. Основные решения

- JSON и реляционные поля содержат факты: сотрудника, действие, даты,
  подразделение, должность, ставку и основания.
- Шаблон определяется сочетанием `организация + сценарий + язык + версия`.
- Тип приказа недостаточен для выбора текста. Например, постоянный и временный
  перевод относятся к переводу, но используют разные преамбулы.
- Нормализованное название хранится отдельно от исходного названия архивного
  документа.
- Нативный DOCX/PDF уже изданного приказа является источником и средством
  проверки смысла, но не обязан дословно определять стандартизированное
  представление.
- Смысл архивного приказа изменять нельзя. Исходный файл должен оставаться
  доступным отдельно от стандартизированного представления.
- Для будущего приказа текст формируется из структурированных данных. Перед
  регистрацией кадровик может исправить языковую версию вручную.
- После регистрации сохраняются версия применённого шаблона и окончательный
  снимок текста на каждом сформированном языке. Последующее изменение шаблона
  не изменяет зарегистрированный приказ.

## 3. Языковая политика организации

Для организации задаются:

```json
{
  "primary_order_language": "kk",
  "secondary_order_language": "ru",
  "generate_bilingual": true
}
```

Основной язык открывается первым и используется для печати по умолчанию.
Переключатель позволяет открыть вторую версию. Для другой организации языки
могут быть поменяны местами без изменения структуры приказа.

В первой реализации отдельный интерфейс настройки организаций не требуется:
для текущего ММЦ используются `kk` как основной и `ru` как дополнительный язык.

## 4. Состав шаблона

Каждый вариант шаблона содержит:

1. стабильный `template_key` и версию;
2. код кадрового сценария;
3. нормализованные названия `kk` и `ru`;
4. преамбулы `kk` и `ru`;
5. правила формирования распорядительных пунктов;
6. дополнительные стандартные распоряжения;
7. допустимые виды оснований;
8. правила объединения связанных действий в один пункт;
9. заключительную часть и подпись.

Минимально подтверждённые варианты:

| Сценарий | Правовая основа из проверенных образцов |
|---|---|
| Приём | статья 34 ТК РК |
| Постоянный перевод | статья 38 ТК РК |
| Временный перевод | статья 41 ТК РК |
| Расторжение по инициативе работника | пункт 5 статьи 49 и пункт 2 статьи 56 ТК РК |
| Доплата или совмещение | статья 111 ТК РК |
| Работа в выходные и праздничные дни | статья 109 ТК РК |
| Изменение рабочего времени | статья 28 ТК РК |

Если структурированных данных недостаточно для однозначного выбора варианта,
система не должна угадывать преамбулу: вариант выбирает кадровик.

## 5. Формирование документа

Вкладка «Документ» показывает единый приказ, а не техническую расшифровку
JSON:

1. нормализованное название;
2. преамбула;
3. `БҰЙЫРАМЫН:` или `ПРИКАЗЫВАЮ:`;
4. связные нумерованные пункты;
5. основания непосредственно после соответствующих пунктов;
6. дополнительные распоряжения;
7. должность и ФИО подписанта.

Несколько нормализованных действий могут образовывать один пункт документа.
Например, перевод и разрешение совмещения одного сотрудника с одной даты могут
быть представлены одной связной распорядительной формулировкой.

## 6. Основания

Основание выбирается из `basis_documents`, а не вводится только свободным
текстом. Редактор пункта должен позволять:

- выбрать вид основания;
- выбрать связанную запись основания, если она существует;
- добавить несколько оснований;
- выбрать «Другое» и ввести текст вручную;
- сохранить исходный импортированный текст без перезаписи.

Строки `Негіз:` и `Основание:` формируются языковыми шаблонами из одного набора
связанных оснований.

## 7. Ручное редактирование

- Изменение структурированных данных обновляет обе автоматически сформированные
  языковые версии.
- Ручная правка казахского текста не должна автоматически переводиться в
  русский текст и наоборот.
- Скорректированная вручную версия помечается как редакционная и не
  перезаписывается автоматической генерацией без явного действия пользователя.
- Команда возврата к шаблону действует только на выбранный язык.

## 8. Граница ближайшей реализации

Ближайшая итерация проверяет концепцию на приказах №104 и №332, сохраняет
переключатель языков, исправляет редактор оснований и печать. Она не включает
редактор каталога шаблонов, настройки нескольких организаций, новые таблицы или
миграции.
