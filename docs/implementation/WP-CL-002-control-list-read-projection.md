## 1. Цель и границы

`WP-CL-002` реализует единственную типизированную серверную проекцию текущего активного персонала для будущего Excel-экспорта. Проекция доступна только в пределах организационного scope вызывающего пользователя, содержит полные ИИН и телефоны и поэтому защищена отдельным permission.

В пакет входят авторизованный внутренний сервис выборки, Pydantic-контракт, регистрация permission, назначение роли и целевые тесты. Публичного HTTP endpoint в `WP-CL-002` нет.

В пакет не входят создание или хранение `.xlsx`, форматирование ячеек, имя и место сохранения файла, frontend, кнопка экспорта, история экспортов, карточка сотрудника и предложения исправлений. Эти границы сохраняют разделение с будущим Excel-пакетом.

## 2. Техническое решение

### 2.1. Внутренний сервис и граница HTTP

Публичный маршрут `GET /directory/personnel/control-list/projection` удалён. JSON с полными ИИН и телефонами представлял бы самостоятельный канал массовой выгрузки ПДн и не нужен будущему Excel-сценарию. Внешнего альтернативного пути к проекции в `WP-CL-002` нет.

Единственная публичная точка сервисного модуля — `build_control_list_projection(engine, user_context=...)`. Она до чтения кадровых данных проверяет эффективный `CONTROL_LIST_EXPORT`, вычисляет штатный personnel visibility scope и только затем вызывает приватный построитель. Ошибки авторизации имеют стабильные коды и сообщения без значений конфигурации, имён классов исключений и внутренних деталей.

Для непустой корректной выборки приватный построитель использует фиксированные пять пакетных `SELECT`: базовые строки, образование, повышение квалификации, телефоны и дополнительный профиль. Все запросы выполняются в одной явной транзакции PostgreSQL `REPEATABLE READ, READ ONLY`. Количество запросов не зависит от числа сотрудников, поэтому загрузка коллекций не создаёт N+1 и декартового размножения.

### 2.2. Дата среза

В начале вызова сервис один раз получает текущее время в IANA-таймзоне из `ORGANIZATION_TIMEZONE`. Без явной настройки используется утверждённое значение `Asia/Almaty`. Настройка должна быть непустым нормализованным IANA key; пустое, неизвестное или синтаксически некорректное значение приводит к контролируемой `ControlListConfigurationError` с постоянным безопасным сообщением без возврата ошибочного значения или деталей исключения.

Из одного значения времени формируются:

- `generated_at` — время построения проекции;
- `as_of_date` — календарная дата среза;
- один параметр `as_of_date`, передаваемый в базовую выборку и все проверки актуальности.

Повторное вычисление текущей даты внутри операции отсутствует. Произвольная и историческая дата во внешнем MVP-контракте не поддерживается.

### 2.3. Состав выборки

Сотрудник включается, если на `as_of_date` одновременно выполняются условия:

- `persons.person_status = 'active'`;
- `employees.operational_status = 'active'`;
- `employees.is_active` не равен `false`;
- период `employees.date_from/date_to` содержит дату среза;
- сотрудник попадает в разрешённый организационный scope;
- существует ровно одно назначение с `active_flag = true`, `is_primary = true`, `lifecycle_status = 'active'`, период которого содержит дату среза.

Вторичные назначения и совместительство не создают строки и не входят в проекцию MVP. Источниками истины не являются `pending`, intake, raw/legacy-поля и таблицы импорта контрольного списка.

Для ограниченного scope кандидат определяется только по текущим основным назначениям: достаточно хотя бы одного активного основного назначения в разрешённом подразделении. После включения кандидата проверяются все его текущие основные назначения, включая находящиеся вне scope; наличие более одного блокирует всю проекцию. `employees.org_unit_id` не используется ни для определения scope, ни как замена текущему назначению.

Сотрудник без текущего основного назначения не может быть надёжно отнесён к ограниченному scope, поэтому scoped-пользователю он не показывается и его выгрузку не блокирует. При organization-wide scope такой сотрудник входит в fail-closed диагностику. Сотрудники, чьи текущие основные назначения полностью вне scope, не попадают ни в данные, ни в диагностику, поэтому их `employee_id` не раскрывается.

## 3. RBAC и организационный scope

### 3.1. Permission и роли

Зарегистрирован отдельный permission:

```text
CONTROL_LIST_EXPORT
```

Миграция назначает его через `access_grants.target_type = 'ROLE'` только единственной платформенной роли с `code = 'HR_HEAD'`; активность самого grant определяется `access_grants.active_flag`.

Решение для MVP:

- permission не назначается всей роли `HR_reg`;
- permission не наследуется автоматически от персонального или ролевого `HR_ENROLLMENT_MANAGER`;
- отдельному пользователю permission можно выдать штатным механизмом персональных grants;
- роль `ADMIN` следует общей модели `access_grants`: специального обхода проверки для контрольного списка нет. ADMIN получает доступ только при наличии эффективного grant по общим правилам проекта.

Обычный доступ к просмотру персонала не позволяет построить внутреннюю проекцию с полными ИИН/телефонами: авторизованный сервисный фасад сначала обязательно проверяет именно `CONTROL_LIST_EXPORT`.

### 3.2. Scope

После permission сервис применяет штатный `compute_scope(..., include_inactive=False)`. Отсутствие personnel visibility преобразуется в типизированную доменную ошибку, а значения scope передаются приватному построителю как:

| Значение | Семантика |
| --- | --- |
| `None` | организация целиком |
| непустой список `unit_id` | только разрешённые подразделения |
| пустой список | нет видимых подразделений; возвращается пустая проекция без запросов к кадровым данным |

Проверка permission и scope выполняется серверным фасадом до любого чтения проекции. Низкоуровневый построитель является приватной деталью модуля и не экспортируется пакетом.

## 4. Типизированный контракт проекции

Внутренний результат использует `schema_version = CONTROL_LIST_EXPORT_V1` и состоит из `metadata`, `total`, `items`.

### 4.1. Метаданные

| Поле | Тип | Правило |
| --- | --- | --- |
| `schema_version` | literal | `CONTROL_LIST_EXPORT_V1` |
| `as_of_date` | `date` | единая дата среза |
| `generated_at` | timezone-aware `datetime` | единое время построения |
| `timezone` | `str` | фактическая IANA-таймзона |
| `initiator_user_id` | `int` | технический идентификатор инициатора из авторизованного серверного контекста |
| `scope.organization_wide` | `bool` | признак полного организационного scope |
| `scope.org_unit_ids` | `list[int] \| null` | отсортированный список подразделений либо `null` |
| `filters` | закрытый объект | в MVP всегда пуст; дополнительные поля запрещены схемой |

### 4.2. Строка

| Будущий столбец | Поле контракта | Тип | Канонический источник и правило |
| --- | --- | --- | --- |
| № | `number` | `int` | присваивается после окончательной сортировки, начиная с 1 |
| Группа подразделений | `org_group` | `str \| null` | `deps_group.group_name` через основное назначение и `org_units.group_id` |
| Подразделение | `org_unit` | `str` | `org_units.name` основного назначения |
| Фамилия, имя, отчество | `full_name` | `str` | нормализованный `persons.full_name` |
| Дата рождения | `birth_date` | `date \| null` | `persons.birth_date` |
| ИИН | `iin` | `str \| null` | `persons.iin`; не приводится к числу |
| Занимаемая должность | `position` | `str \| null` | `positions.name` основного назначения |
| Категория должности | `position_category` | `str \| null` | `positions.category` |
| Ставка | `employment_rate` | `Decimal \| null` | `person_assignments.rate` |
| Дата начала в должности | `assignment_start_date` | `date` | `person_assignments.start_date` |
| Образование, год окончания, специальность | `education[]` | типизированная коллекция | активные подтверждённые `person_education`; связанные данные остаются одним элементом |
| Повышение квалификации | `training[]` | типизированная коллекция | активные подтверждённые `person_training` |
| Учёная степень | `academic_degrees[]`, `academic_degrees_none` | типизированная коллекция и `bool` | канонические `additional_profile.academic_degrees` и признак подтверждённого отсутствия `academic_degrees_none` |
| Награды | `awards[]`, `awards_none` | типизированная коллекция и `bool` | канонические `additional_profile.awards` и признак подтверждённого отсутствия `awards_none` |
| Телефоны | `phones[]` | типизированная коллекция | активные непустые `contacts.phone`, повторы по нормализованному номеру удаляются |
| ID сотрудника | `employee_id` | `int` | `employees.employee_id` |

`education[]` содержит `record_id`, организацию, связанный год окончания, специальность и даты периода. `training[]` содержит `record_id`, название, организацию, часы, период и номер сертификата. Степени и награды сохраняют канонический порядок JSON-массива через `ordinal`. Телефоны остаются строками и сохраняют исходное отображаемое значение.

Поля без канонического источника не добавлены: пол, национальность, квалификационная категория, примечание, профессиональная группа и стаж.

Для отсутствующих частичных данных скаляр возвращается как `null`, коллекция — как `[]`. Флаги `academic_degrees_none` и `awards_none` сохраняют отличие незаполненных сведений от явно подтверждённого отсутствия. `missing_fields` не считает поле пропущенным, если соответствующий признак подтверждённого отсутствия равен `true`.

## 5. Детерминированный порядок

Строки сортируются в приложении после полной пакетной загрузки:

```text
Группа подразделений (null последними)
→ Подразделение
→ ФИО
→ employee_id
```

Текст сравнивается после нормализации пробелов и `casefold`. После сортировки назначается `number`.

Коллекции сортируются так:

| Коллекция | Порядок |
| --- | --- |
| `education` | дата окончания по возрастанию (`null` последними) → дата начала → организация → `record_id` |
| `training` | дата окончания по убыванию (`null` последними) → дата начала по убыванию → название → `record_id` |
| `academic_degrees` | порядок канонического JSON-массива (`ordinal`) |
| `awards` | порядок канонического JSON-массива (`ordinal`) |
| `phones` | нормализованный номер → `contact_id`, затем удаление повторов номера |

Excel-пакет может сериализовать эти коллекции переносами строк, но не должен менять связи внутри элемента образования или повторно определять порядок.

## 6. Диагностика назначений

Если в определённой правилами раздела 2.3 области есть активный сотрудник с нарушением инварианта назначения, сервис прекращает построение до загрузки коллекций и не возвращает частичный результат. Ошибка остаётся типизированной доменной `ControlListAssignmentConflict`; её HTTP-отображение отложено до единственного Excel-endpoint в `WP-CL-003`.

Детали ошибки соответствуют схеме `ControlListAssignmentConflictDetail`:

```json
{
  "code": "CONTROL_LIST_ASSIGNMENT_CONFLICT",
  "message": "Active primary assignment invariant is violated.",
  "schema_version": "CONTROL_LIST_EXPORT_V1",
  "as_of_date": "2026-09-03",
  "conflicts": [
    {
      "employee_id": 42,
      "violation": "MISSING_PRIMARY_ASSIGNMENT"
    }
  ]
}
```

Допустимые значения `violation`: `MISSING_PRIMARY_ASSIGNMENT` и `MULTIPLE_PRIMARY_ASSIGNMENTS`. Конфликты отсортированы по `employee_id`. `assignment_count`, ФИО, ИИН, телефон и другие избыточные сведения отсутствуют. Ошибки авторизации и конфигурации также используют постоянные безопасные коды/сообщения; содержимое проекции, ИИН и телефоны не журналируются.

## 7. Аудит и граница Excel-пакета

Внутренний сервис в `WP-CL-002` не является пользовательской операцией скачивания и не записывает ложное событие успешного Excel-экспорта. Публичного массового read endpoint в этом пакете нет.

Единственный Excel-endpoint, HTTP-отображение доменных ошибок, аудит результата операции и заголовки `Cache-Control: no-store` для ответа с ПДн реализуются совместно в `WP-CL-003`. Аудит должен фиксировать пользователя, время, scope, фильтры и успех/ошибку. Если политика потребует отдельно учитывать построение внутренней проекции, такое событие должно отличаться от события создания/скачивания файла.

## 8. Миграция

Миграция `w6x7y8z9a0b1_wp_cl_002_control_list_export_permission.py`:

- считает `CONTROL_LIST_EXPORT` новой принадлежащей ей записью и создаёт её только при полном отсутствии такого кода;
- при заранее существующем permission завершается контролируемой ошибкой, не изменяет существующую запись и не создаёт частичный grant;
- требует ровно одну платформенную роль с `code = 'HR_HEAD'`; таблица `roles` не содержит признака `is_active`;
- выдаёт эффективный ROLE grant только `HR_HEAD`;
- не создаёт grants для `HR_reg`, `HR_ENROLLMENT_MANAGER` или `ADMIN`;
- при downgrade удаляет только собственный grant с точной причиной;
- при downgrade удаляет свой HR_HEAD grant;
- удаляет permission только при полном отсутствии оставшихся grants, сохраняя permission и любые появившиеся после upgrade персональные или иные grants.

`down_revision`: `v5w6x7y8z9a`.

Production validation 2026-09-03 выявила, что первоначальная версия миграции ошибочно обращалась к отсутствующей колонке `roles.is_active`. Миграция исправлена под фактическую схему `roles(role_id, name, code)`. Реальный PostgreSQL-тест проходит полную цепочку `v5w6x7y8z9a → head → v5w6x7y8z9a`, включая audit-изменение следующей ревизии `x7y8z9a0b1c2`.

## 9. Тесты и критерии приёмки

Целевые тесты покрывают:

- запрет без `CONTROL_LIST_EXPORT` и отсутствие специального ADMIN-bypass;
- передачу организационного scope и пустой scope;
- одну строку на сотрудника и использование только основного назначения;
- условия активности person, employee и назначения на единую дату;
- агрегирование отсутствующих и множественных основных назначений;
- отказ от частичного результата;
- одно вычисление времени/даты среза;
- стабильную сортировку строк, нумерацию и порядок коллекций;
- `null` и пустые коллекции для отсутствующих частичных данных;
- возврат полных ИИН и телефонов только через авторизованный внутренний фасад;
- отсутствие зависимостей от intake, raw, pending и импортного staging;
- отсутствие кадровых мутаций;
- фиксированное число пакетных запросов без N+1;
- PostgreSQL-реализацию `ANY(:ids)`, CTE/JOIN, отсутствие декартового размножения и границы дат;
- фактические `REPEATABLE READ`, `READ ONLY` и единый snapshot при параллельном изменении;
- scope-сценарии внутри/вне области, scoped и organization-wide отсутствие назначения и отсутствие утечки `employee_id`;
- эквивалентные номера телефонов с разным написанием `+`;
- RBAC-матрицу `HR_HEAD`, `HR_reg`, только `HR_ENROLLMENT_MANAGER`, персональный grant, а также `ADMIN` с permission и без него;
- реальные PostgreSQL upgrade/downgrade-тесты миграции, конфликт существующего permission, атомарность ошибки и сохранение позднего персонального grant.

Критерии приёмки `WP-CL-002`:

1. Авторизованный внутренний фасад защищён новым permission и штатным scope; публичный endpoint отсутствует.
2. Валидная выборка имеет одну строку на активного сотрудника по единственному основному назначению.
3. Любая неоднозначность назначения возвращает полный список конфликтов и ни одной строки данных.
4. Контракт содержит все утверждённые поля первой версии как скаляры или типизированные коллекции.
5. Результат детерминирован при неизменных данных и дате среза.
6. Проекция read-only и не создаёт Excel-файл либо аудит скачивания.
7. Целевые тесты, lint/format и `git diff --check` проходят.
