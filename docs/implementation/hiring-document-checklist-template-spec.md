# Corpsite: редактируемый перечень документов при приёме на работу

**Статус:** Ready for Implementation  
**Модуль:** Персонал → Личные карточки → регистрация претендента  
**Рабочий экран:** `/directory/personnel/lk?record_kind=applicant`  
**Тип документа:** универсальная печатная памятка, не связанная с конкретным претендентом

## 1. Назначение

При регистрации бумажного кадрового обращения сотрудник отдела кадров должен иметь возможность быстро открыть и распечатать для претендента актуальный перечень документов при приёме на работу.

Перечень является универсальным:

- не относится к конкретной записи претендента;
- не содержит ИИН, Ф. И. О., должность или дату;
- может дополняться от руки после печати;
- редактируется руководителем отдела кадров без изменения программного кода и без нового развёртывания приложения.

## 2. Согласованные продуктовые решения

1. Отдельная пользовательская страница «Претенденты» не создаётся.
2. Основная страница личных карточек и её панель фильтров не получают новых кнопок.
3. Кнопка печати размещается в выдвижном окне **«Зарегистрировать претендента»**.
4. Кнопка доступна до ввода и проверки ИИН.
5. Печатный документ не связывается с заявкой, человеком или личной карточкой.
6. Актуальная редакция хранится на backend в PostgreSQL.
7. Печатать перечень могут сотрудники, которым разрешена регистрация претендентов.
8. Редактировать шаблон может только пользователь с отдельным разрешением, первоначально выданным руководителю отдела кадров.
9. Проверка доступа выполняется на backend; скрытие кнопки на frontend не считается защитой.
10. Произвольный исполняемый HTML или JavaScript в шаблоне не допускается.

## 3. Пользовательский интерфейс

### 3.1. Окно регистрации претендента

В выдвижном окне под пояснением **«Регистрация бумажного кадрового обращения»** и над полем ИИН располагается строка действий.

Для сотрудника отдела кадров:

- **Распечатать перечень документов** — вторичная кнопка с иконкой печати.

Для руководителя отдела кадров дополнительно:

- **Редактировать шаблон** — спокойная вторичная кнопка или текстовая кнопка с иконкой редактирования.

Существующая красная текстовая ссылка заменяется этими элементами. Красный цвет не используется, поскольку действие не является ошибкой или предупреждением.

### 3.2. Предварительный просмотр и печать

Нажатие **«Распечатать перечень документов»** открывает актуальную редакцию шаблона в печатном представлении. Предпочтителен отдельный технический маршрут/вкладка для печати, чтобы не печатать фон, drawer и остальные элементы страницы.

Печатное представление содержит:

- заголовок;
- упорядоченный список с пустыми квадратами для ручных отметок;
- примечание;
- необязательный блок **«Дополнительные документы и отметки»** с настраиваемым количеством пустых строк;
- экранные кнопки **«Распечатать»** и **«Закрыть»**, скрываемые правилами `@media print`.

Автоматический вызов печати при открытии не выполняется. Пользователь сначала видит документ, затем нажимает **«Распечатать»**.

### 3.3. Редактор шаблона

Редактор предназначен для кадрового работника и не должен требовать знания HTML или Markdown.

Он позволяет:

- изменить заголовок;
- изменить текст любого пункта;
- добавить пункт;
- удалить пункт;
- переместить пункт вверх или вниз;
- изменить примечание;
- включить или отключить блок рукописных дополнений;
- задать разумное количество пустых строк;
- просмотреть результат до сохранения;
- сохранить или отменить изменения.

В первой версии не требуется полноценный текстовый процессор, загрузка DOCX, настройка шрифтов, цветов или произвольной вёрстки.

## 4. Первоначальное содержание

### Заголовок

**Краткий перечень документов при приёме на работу**

### Пункты

1. **Документ, удостоверяющий личность.**
2. **Документ об образовании и квалификации** — диплом, сертификат, лицензия или иной документ, если работа требует соответствующих знаний, квалификации или подготовки.
3. **Документ, подтверждающий трудовую деятельность** — для лиц, имеющих трудовой стаж.
4. **Документ о прохождении предварительного медицинского осмотра** — если его прохождение обязательно для соответствующей должности.
5. **Справка о наличии либо отсутствии судимости** — в случаях, предусмотренных законодательством. Справку можно получить на портале eGov.kz.

### Примечание

> Точный перечень документов определяется в зависимости от должности и сообщается сотрудником отдела кадров.

### Рукописное дополнение

По умолчанию показывается блок **«Дополнительные документы и отметки»** с тремя пустыми строками.

## 5. Хранение данных

Перед разработкой необходимо проверить существующие модели системных шаблонов, организационных настроек, аудита и версионирования. Если подходящий механизм уже есть, его следует переиспользовать.

Если подходящего механизма нет, рекомендуется минимальная предметная модель кадровых шаблонов.

### 5.1. Текущая редакция

Логическая структура записи:

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ |
| `organization_id` | Организация, если данные проекта имеют организационный scope |
| `code` | Стабильный код `HIRING_DOCUMENT_CHECKLIST` |
| `title` | Заголовок документа |
| `content` | Структурированное JSON-содержимое |
| `version` | Монотонно возрастающий номер редакции |
| `created_at` | Дата создания |
| `updated_at` | Дата последнего изменения |
| `updated_by_user_id` | Автор последнего изменения |

Рекомендуемое содержимое `content`:

```json
{
  "schema_version": 1,
  "items": [
    {"id": "stable-item-id", "text": "Текст пункта"}
  ],
  "note": "Заключительное примечание",
  "show_additional_notes": true,
  "additional_notes_lines": 3
}
```

Порядок элементов массива является порядком печати. Идентификатор пункта нужен для стабильного редактирования на frontend и не выводится на бумагу.

### 5.2. История редакций

Каждое успешное сохранение создаёт запись истории либо событие в существующей системе аудита со снимком содержимого до/после изменения.

Должны быть установимы:

- код шаблона;
- номер редакции;
- предыдущее и новое содержимое;
- пользователь;
- дата и время изменения.

Просмотр и восстановление истории через UI не являются обязательными для первой версии, но данные истории должны сохраняться, чтобы восстановление было возможно административным способом.

### 5.3. Начальная запись

Первоначальный шаблон создаётся миграцией или принятым в проекте механизмом seed-данных. Операция должна быть идемпотентной и не перезаписывать последующие изменения отдела кадров.

## 6. Права доступа

### Просмотр и печать

Используется существующее право, которое разрешает открывать форму и регистрировать претендента. Не следует создавать дополнительное право только для печати, если оно не улучшает действующую модель безопасности.

### Редактирование

Если подходящего разрешения нет, добавить:

`HR_DOCUMENT_TEMPLATE_EDIT`

Первоначально разрешение назначается роли `HR_HEAD`. Проверку названия роли в компонентах или API не выполнять: доступ определяется permission-механизмом проекта.

`ADMIN` не получает неявный обход проверки, если в проекте применяется явное назначение разрешений.

## 7. API-контракт

Точные маршруты необходимо согласовать с существующими conventions проекта. Рекомендуемый контракт:

### Получение актуального шаблона

`GET /directory/personnel/document-templates/hiring-document-checklist`

Ответ содержит:

- `code`;
- `title`;
- структурированное `content`;
- `version`;
- `updated_at`;
- безопасное отображаемое имя или идентификатор автора, если это принято в проекте;
- `can_edit` либо frontend получает это право из существующего permission-контекста.

### Изменение шаблона

`PUT /directory/personnel/document-templates/hiring-document-checklist`

Запрос содержит:

- `expected_version`;
- `title`;
- `content`.

Backend:

1. проверяет `HR_DOCUMENT_TEMPLATE_EDIT`;
2. проверяет организационный scope;
3. валидирует содержимое;
4. сравнивает `expected_version` с текущей версией;
5. при совпадении атомарно сохраняет новую редакцию и аудит;
6. при несовпадении возвращает `409` с понятным кодом конфликта редакций.

## 8. Валидация и безопасность

- Заголовок обязателен.
- Должен существовать хотя бы один непустой пункт.
- Пустые пункты не сохраняются.
- Для заголовка, пункта и примечания задаются разумные ограничения длины.
- `additional_notes_lines` ограничивается небольшим диапазоном, например `0–10`.
- Произвольный HTML и скрипты не принимаются.
- Текст отображается безопасными средствами React.
- Обновление текущей редакции и запись истории выполняются в одной транзакции.
- Организационная принадлежность не принимается на доверии из тела запроса, а определяется сервером из контекста пользователя.

## 9. Конкурентное редактирование

Редактор загружает номер текущей версии и передаёт его как `expected_version`.

Если другой пользователь уже сохранил новую редакцию, сервер возвращает конфликт. Интерфейс не перезаписывает изменения молча и предлагает:

- загрузить актуальную редакцию;
- повторно внести изменения.

Автоматическое слияние текста в первой версии не требуется.

## 10. Требования к печати

- Формат: A4, книжная ориентация.
- Документ с начальным содержимым помещается на одну страницу.
- Основной текст остаётся читаемым; недопустимо уменьшать шрифт ради принудительного размещения чрезмерно большого шаблона.
- Экранная навигация, кнопки и фон приложения не печатаются.
- Фон документа белый.
- Пустые квадраты и линии для рукописных записей хорошо видны.
- Длинный пользовательский шаблон может перейти на следующую страницу без обрезки текста.
- Печатная страница повторно получает актуальный шаблон с backend или использует однозначно переданную текущую редакцию; устаревший встроенный fallback не подменяет ошибку загрузки.

## 11. Обработка ошибок

- Ошибка загрузки: понятное сообщение и действие **«Повторить»**.
- Ошибка сохранения: введённый текст остаётся в редакторе.
- Конфликт версии: отдельное сообщение о том, что шаблон уже изменён.
- Нет права: backend возвращает `403`; frontend не показывает кнопку редактирования.
- Начальный шаблон отсутствует: диагностируемая серверная ошибка; приложение не создаёт новую запись при обычном GET-запросе.

## 12. Не входит в первую версию

- Персонализация памятки по Ф. И. О., ИИН, должности или заявке.
- Учёт фактически сданных документов.
- Подпись претендента.
- Хранение распечатанной копии в карточке.
- Отметка факта печати.
- DOCX/PDF как редактируемый источник.
- Полноценный WYSIWYG-редактор.
- Разные шаблоны для каждой должности.
- Пользовательский интерфейс просмотра и восстановления истории редакций.

## 13. Тестирование

### Backend

- получение начального шаблона;
- доступ к чтению в допустимом кадровом контексте;
- запрет редактирования без permission;
- успешное редактирование с permission;
- назначение permission роли `HR_HEAD` миграцией;
- валидация пустого заголовка, пустого списка и слишком длинных значений;
- защита от HTML/script payload;
- увеличение версии;
- создание истории/аудита;
- `409` при устаревшем `expected_version`;
- соблюдение организационного scope;
- идемпотентность начального seed.

### Frontend

- кнопка печати отображается в drawer до ввода ИИН;
- красная ссылка удалена;
- обычный кадровик не видит редактирование;
- руководитель с permission видит редактирование;
- добавление, удаление и изменение порядка пунктов;
- предварительный просмотр;
- сохранение и отмена;
- сохранение пользовательского ввода при ошибке;
- обработка конфликта версии;
- экранные кнопки скрываются при печати.

### Ручная проверка

1. Открыть `/directory/personnel/lk?record_kind=applicant`.
2. Нажать **«Зарегистрировать претендента»**.
3. Убедиться, что кнопка печати доступна при пустом ИИН.
4. Открыть печатный вид обычным сотрудником отдела кадров.
5. Проверить одну страницу A4 с начальным текстом.
6. Убедиться, что на бумаге нет элементов интерфейса.
7. Войти руководителем отдела кадров.
8. Изменить пункт, добавить новый пункт и переставить его.
9. Сохранить и повторно открыть печатный вид.
10. Убедиться, что новая редакция используется сразу.
11. Проверить, что обычный сотрудник видит новую редакцию, но не может её изменить.

## 14. Этапы реализации

### Итерация 1 — полный рабочий контур

1. Инвентаризация существующих механизмов шаблонов, настроек, permissions и аудита.
2. Модель и миграция/seed.
3. Permission для редактирования.
4. Backend API и тесты.
5. Кнопки в drawer.
6. Редактор и печатное представление.
7. Frontend-проверки и локальный smoke.

### Итерация 2 — визуальная приёмка

1. Проверка скриншота drawer.
2. Проверка browser print preview.
3. Коррекция отступов, размеров, подписей и печатной вёрстки.
4. Повторные тесты.

После локальной приёмки отдельно выполняются commit, push, миграция и развёртывание по принятому процессу проекта.

## 15. Критерии готовности

Функция считается готовой, когда:

- кнопка печати находится только в окне регистрации претендента;
- перечень открывается без ввода ИИН;
- персональные поля отсутствуют;
- начальный текст соответствует разделу 4;
- лист корректно печатается;
- руководитель отдела кадров может изменить шаблон без deployment;
- остальные кадровые пользователи не могут его изменить;
- изменения сразу отражаются в следующем предварительном просмотре;
- сохраняются автор, время, версия и история изменения;
- конфликт одновременного редактирования не приводит к молчаливой потере данных;
- миграции и релевантные тесты проходят локально;
- посторонние файлы и незавершённые изменения рабочего дерева не затронуты.
