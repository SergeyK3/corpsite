# Проектирование: управление шаблонами кадровых приказов

> Статус: проектирование. Документ задаёт целевую модель и не вносит изменений в действующие генераторы, данные или жизненный цикл приказов.

## 1. Назначение

Нужен единый административный инструмент управления шаблонами. В сайдбаре системного администратора появляется один пункт **«Шаблоны»**, ведущий на страницу `/admin/templates`.

На странице предусматриваются два раздела:

- «Шаблоны задач»;
- «Шаблоны кадровых приказов».

Существующая страница «Шаблоны регулярных задач» переносится в первый раздел без изменения её функциональности, данных и правил доступа. Второй раздел предназначен для управляемых версий шаблонов кадровых приказов.

## 2. Цели

- Централизованно создавать и редактировать шаблоны кадровых приказов.
- Переиспользовать уже существующие генераторы и editorial blocks.
- Восстанавливать черновики приказов по данным PDF-журнала.
- Поддерживать RU/KK.
- Создавать новые шаблоны и новые версии на основе существующих.
- Впоследствии разгрузить вкладку «Данные» редактора приказа, перенеся в описание шаблона устойчивые правила полей и представления.

## 3. Не входит в первый этап

- Автоматическое изменение уже зарегистрированных приказов.
- Массовое применение реконструированных приказов.
- Произвольный raw JSON или исполняемый код в браузере.
- Автоматическое придумывание отсутствующих реквизитов.
- Немедленная замена всех существующих генераторов.

## 4. Начальный каталог кадровых шаблонов

Начальный каталог включает следующие типы. Системные коды на первом этапе сопоставляются с фактически применяемыми `order_type_code` и `item_type_code`; создание нового параллельного набора кодов не предполагается.

| Название | Назначение |
| --- | --- |
| Приём на работу | Оформление приёма сотрудника. |
| Перевод | Изменение должности, подразделения, ставки или иных условий перевода. |
| Увольнение | Прекращение трудовых отношений. |
| Предоставление ежегодного отпуска | Оформление ежегодного оплачиваемого отпуска. |
| Предоставление отпуска без содержания | Оформление отпуска без сохранения заработной платы. |
| Предоставление отпуска по уходу за ребёнком | Оформление начала отпуска по уходу за ребёнком. |
| Выход на работу из отпуска по уходу за ребёнком | Оформление выхода после такого отпуска. |
| Начало совмещения | Оформление начала совмещения. |
| Прекращение совмещения | Оформление прекращения совмещения. |
| Доплата | Оформление доплаты. |

«Предоставление отпуска по уходу за ребёнком» и «Выход на работу из отпуска по уходу за ребёнком» — разные типы: их нельзя смешивать в одном шаблоне, версии или правиле выбора полей.

## 5. Структура шаблона

Каждый шаблон и каждая его версия описывают следующие управляемые элементы:

| Элемент | Содержание |
| --- | --- |
| Системный код типа | Ссылка на действующий `order_type_code` и применимые `item_type_code`. |
| Название RU/KK | Отображаемые названия шаблона на русском и казахском языках. |
| Преамбула RU/KK | Двуязычное вводное основание документа. |
| Распорядительное слово | Например, утверждённое языковое представление слова «ПРИКАЗЫВАЮ» / его казахского аналога. |
| Основной текст | Составляемые по контролируемым переменным пункты приказа. |
| Поля | Обязательные и необязательные реквизиты с источником и правилами проверки. |
| Основания | Допустимые виды оснований и условия их обязательности. |
| Форматирование | Правила представления ФИО, дат, должности, отделения и ставки. |
| Общие блоки | Подпись директора, ознакомление и исполнитель. |
| Предупреждения | Сообщения о неполных, неподтверждённых или несовместимых реквизитах. |
| Предпросмотр | Формирование RU/KK представления до публикации и перед созданием приказа. |
| История | Неизменяемая история версий и действий с ними. |

Общие footer-блоки подписи директора, ознакомления и исполнителя хранятся и используются как общие presentation blocks. Они не дублируются внутри конфигурации каждого шаблона.

## 6. Переменные

Текст шаблона использует только контролируемые переменные из справочника, например:

```text
{{employee.full_name_ru}}
{{employee.full_name_kk}}
{{position.title_ru_genitive}}
{{position.title_kk}}
{{org_unit.title_ru_genitive}}
{{org_unit.title_kk}}
{{rate}}
{{effective_date_ru}}
{{effective_date_kk}}
```

- Доступные переменные выбираются из типизированного справочника с описанием источника, языка, обязательности и формата.
- Произвольные выражения, вычисления и исполняемый код запрещены как в браузере, так и в конфигурации шаблона.
- Публикация невозможна, если обнаружены неизвестные переменные или отсутствуют обязательные переменные.
- Сохранённые и подтверждённые должность и отделение имеют приоритет над эвристическим переводом либо выводом из текущего справочника.
- Предпросмотр показывает источник значения и предупреждение, когда значение отсутствует или не подтверждено.

## 7. Версионирование

Версия шаблона имеет один из статусов:

- `DRAFT` — редактируемая, не используется для новых приказов;
- `PUBLISHED` — опубликованная версия, доступная для новых приказов;
- `ARCHIVED` — сохранённая историческая версия, недоступная для новых приказов.

Правила версионирования:

- Опубликованная версия применяется к новым приказам.
- Приказ сохраняет идентификатор версии и снимок сформированного текста.
- Изменение шаблона не изменяет зарегистрированные, подписанные и применённые приказы.
- Существующий черновик можно пересоздать только отдельной командой с preview и явным подтверждением пользователя.
- Публикация и архивирование фиксируются в append-only audit.
- Должна существовать возможность создать новый шаблон или новую версию на основе существующего шаблона либо версии.
- Безопасный rollback активной версии выполняется переключением на ранее опубликованную совместимую версию; это не переписывает уже созданные приказы и их снимки.

## 8. Восстановление по PDF-журналу

Реконструкция применяется, когда из PDF-журнала известны номер, дата, тип приказа и фигурант. Если в документе имеется дата действия, она используется как отдельный подтверждённый реквизит.

Сценарий восстановления:

1. По известным реквизитам выбирается тип и создаётся только черновик приказа.
2. Отсутствующие поля не выдумываются и не заполняются эвристикой без явного подтверждения.
3. Черновик получает предупреждения и статус необходимости кадровой проверки.
4. Для каждого реквизита сохраняются источник (PDF, справочник, ручное подтверждение) и степень подтверждённости.
5. Регистрация и применение доступны только после проверки кадровиком всех требуемых реквизитов.

Реконструкция не означает автоматического связывания исторического события с приказом и не изменяет уже существующие кадровые события.

## 9. Интерфейс

Раздел «Шаблоны кадровых приказов» содержит:

- каталог шаблонов с названием RU/KK, системным типом, текущей опубликованной версией и её статусом;
- фильтры по типу и статусу;
- переход к истории версий и к текущей опубликованной версии;
- редактор версии с разделами «Состав», «Русский», «Қазақша», «Поля», «Основания», «Предпросмотр», «История»;
- действия «Создать черновик версии», «Создать на основе», «Предпросмотр», «Опубликовать», «Архивировать».

В редакторе «Состав» связывает шаблон с поддерживаемыми типами и переиспользуемыми блоками; языковые разделы редактируют только разрешённый текст и размещение переменных. Раздел «Предпросмотр» показывает RU/KK документ с диагностикой полей без выполнения произвольного кода.

## 10. Использование существующей реализации

Новый инструмент не создаёт параллельный генератор приказов. Он описывает и версионирует входные данные для уже существующей реализации и переиспользует:

- `order_type_code` и `item_type_code`;
- существующие editorial generators;
- RU/KK presentation blocks;
- document review;
- lifecycle/editorial audit;
- существующее форматирование дат и должностей;
- существующий печатный footer;
- typed API без raw payload в браузере.

## 11. Пилотный шаблон

Первым полностью управляемым шаблоном становится:

- «Выход на работу из отпуска по уходу за ребёнком»;
- «Бала күтіміне байланысты демалыстан жұмысқа шығу туралы».

На пилоте проверяются:

- RU/KK;
- должность;
- отделение;
- ставка;
- дата действия;
- личное заявление;
- общий footer;
- preview;
- клонирование;
- публикация версии.

Пилот не подменяет действующий генератор: его результат сопоставляется с существующим document review и правилами жизненного цикла до расширения на другие типы.

## 12. Этапы реализации

1. Навигация и перенос шаблонов задач в раздел «Шаблоны».
2. Read-only каталог кадровых шаблонов, построенный на существующих генераторах.
3. Версионирование и редактор пилотного шаблона.
4. Клонирование шаблонов и версий.
5. Последовательный перенос остальных типов.
6. Использование описания полей шаблона для упрощения вкладки «Данные» редактора приказа.

## 13. Открытые решения

До реализации следует зафиксировать решения по следующим вопросам:

- Кто может редактировать и публиковать: системный администратор, `HR_HEAD` или требуется разделение полномочий?
- Допустимо ли иметь несколько одновременно опубликованных вариантов одного типа?
- Как применять новую опубликованную версию к уже существующим черновикам?
- Нужно ли отдельное согласование юридических формулировок?
- Хранить presentation blocks нормализованно или одной versioned-конфигурацией?
- Каков порядок локализации должностей и подразделений, включая источник подтверждённого перевода и допустимые fallback-правила?

## 14. Критерии готовности

| Этап | Проверяемые критерии готовности |
| --- | --- |
| 1. Навигация и перенос | В сайдбаре системного администратора есть один пункт «Шаблоны»; `/admin/templates` содержит два раздела; раздел регулярных задач сохраняет прежнюю функциональность. |
| 2. Read-only каталог | Каталог показывает фактически поддерживаемые типы и текущую опубликованную версию, не создавая параллельный генератор и не меняя приказов. |
| 3. Пилот | Для пилотного типа доступны `DRAFT`/`PUBLISHED`/`ARCHIVED`, preview RU/KK, проверка переменных, общий footer и append-only audit публикации. |
| 4. Клонирование | Пользователь может безопасно создать новый шаблон или черновик версии на основе существующего; исходная версия остаётся неизменной. |
| 5. Последовательный перенос | Каждый новый тип проходит проверку существующего генератора, RU/KK preview, обязательных полей и правил document review до публикации. |
| 6. Упрощение «Данных» | Вкладка «Данные» использует описание полей шаблона, не теряя обязательных проверок, typed API и возможности ручной кадровой проверки. |

Обязательные гарантии для всех этапов:

- отсутствует ретроактивное изменение приказов;
- каждый приказ хранит снимок применённой версии и сформированного текста;
- доступен preview RU/KK;
- публикация и архивирование имеют audit-запись;
- неизвестные переменные запрещают публикацию;
- система не создаёт выдуманные данные при реконструкции или формировании приказа;
- доступен безопасный rollback активной версии без изменения созданных приказов.
