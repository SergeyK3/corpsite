# Задание для Cursor: реестр входящей информации и контроль исполнения

## Контекст

В системе уже ведётся реестр производственных приказов. Сейчас процесс начинается с готового приказа, однако не фиксируется основание, из которого возникло управленческое действие: письмо, служебная или докладная записка, рапорт, жалоба, заявление, акт, предписание и т. п.

Нужно добавить отдельный модуль **«Входящая информация»**, который отвечает на вопросы:

- что и когда поступило;
- кто направил документ и кому он адресован;
- какое решение принято;
- кому поручено исполнение и в какой срок;
- к какому результату привело рассмотрение;
- какие приказы и другие документы возникли на основании входящей информации.

Реестр входящей информации не заменяет реестр приказов. Он является началом процесса и связывается с приказами через устойчивые идентификаторы.

## Задача

Изучи текущий репозиторий, его архитектуру, модели данных, роли, маршруты, компоненты интерфейса, соглашения по именованию и тестированию. После этого реализуй модуль регистрации, рассмотрения и контроля исполнения входящей информации в рамках существующего стека и визуального языка проекта.

Не создавай отдельное приложение и не дублируй уже существующие сущности пользователей, сотрудников, подразделений, файлов, приказов или справочников. Используй существующие сущности и связи, если они есть.

## 1. Основная сущность

Рабочее название сущности: `IncomingDocument` / «Входящая запись».

Обязательные поля:

| Поле | Требование |
|---|---|
| ID | Внутренний неизменяемый идентификатор |
| Регистрационный номер | Уникальный человекочитаемый номер, например `ВХ-2026-0042`; генерация на сервере, без гонок |
| Дата поступления | Когда документ фактически получен |
| Дата регистрации | Когда документ зарегистрирован |
| Тип документа | Значение из справочника |
| От кого | Физическое лицо, сотрудник, подразделение или внешняя организация; допускается текстовое значение, если контрагента нет в системе |
| Кому адресовано | Пользователь, сотрудник, подразделение или должность |
| Краткое содержание | Суть вопроса без необходимости открывать файл |
| Канал поступления | Бумага, электронная почта, внутренняя система, лично, иное |
| Ссылка/вложение | Один или несколько файлов либо ссылка на существующее файловое хранилище |
| Текущий статус | Значение из справочника статусов |
| Автор и время создания | Аудит |
| Последний редактор и время изменения | Аудит |

Дополнительные поля процесса:

- резолюция руководителя;
- основной исполнитель;
- соисполнители (0..N);
- срок исполнения;
- планируемый результат;
- дата фактического исполнения;
- результат исполнения;
- контролёр;
- дата закрытия;
- примечание;
- уровень приоритета;
- признак контрольного документа;
- основание для продления срока и новая дата срока;
- причина отмены или передачи по компетенции.

## 2. Справочники

### Тип документа

Предусмотри начальные значения:

- письмо;
- служебная записка;
- докладная записка;
- объяснительная записка;
- рапорт;
- заявление работника;
- жалоба / обращение;
- представление;
- акт;
- предписание;
- протокол;
- заявка;
- уведомление;
- запрос;
- поручение руководителя;
- документ контролирующего органа;
- судебный / исполнительный документ;
- иной документ.

### Планируемый результат

- принять к сведению;
- дать ответ;
- провести проверку;
- подготовить приказ;
- подготовить служебную записку;
- устранить нарушение;
- рассмотреть вопрос об ответственности;
- выплатить / выделить средства;
- внести изменения в документ;
- передать по компетенции;
- отказать с обоснованием;
- оставить без дальнейшего действия;
- иной результат.

### Статус

- Зарегистрировано
- На рассмотрении
- Назначен исполнитель
- В работе
- Ожидает информации
- Подготовлен проект
- На согласовании
- Исполнено
- Закрыто
- Передано по компетенции
- Отменено

`Просрочено` не хранить как ручной постоянный статус. Вычислять его по правилу: срок исполнения меньше текущей даты, запись не закрыта и не отменена. Если архитектура проекта требует хранения признака, он должен обновляться автоматически и не редактироваться пользователем.

Справочники должны расширяться администратором без изменения кода, если в проекте уже есть механизм управляемых справочников. Не удалять используемые значения физически — применять деактивацию.

## 3. Бизнес-процесс

1. Регистратор создаёт запись, заполняет реквизиты и прикладывает исходный документ.
2. Руководитель рассматривает запись и фиксирует резолюцию.
3. Назначаются основной исполнитель, соисполнители, контролёр и срок.
4. Исполнитель ведёт работу и указывает ожидаемый результат.
5. Если требуется приказ, создаётся или привязывается запись из реестра производственных приказов.
6. Исполнитель фиксирует результат и дату исполнения.
7. Контролёр проверяет результат и закрывает запись либо возвращает её в работу с комментарием.

Для жалобы или рапорта нельзя автоматически формировать решение «наказать». Корректная последовательность: регистрация → проверка обстоятельств → заключение → решение → при необходимости дисциплинарный приказ.

## 4. Связь с приказами и результатами

Реализуй связь many-to-many между входящими записями и производственными приказами, если это соответствует текущей модели:

- одна входящая запись может породить несколько приказов или результатов;
- один приказ может иметь несколько оснований;
- связь должна хранить тип связи или комментарий при необходимости;
- в карточке входящей записи показывать связанные приказы: номер, дата, тема, статус и переход в карточку;
- в карточке приказа показывать его основания с регистрационными номерами и переходами.

Если сущности приказа в проекте пока нет, создай абстракцию связи с результатом (`RelatedDocument` / `Outcome`) так, чтобы приказ можно было подключить позднее без переделки основной таблицы. Не сохраняй номера приказов одной текстовой строкой.

## 5. Интерфейс

### Список

Добавь страницу «Входящая информация» со следующими возможностями:

- таблица с регистрационным номером, датой регистрации, типом, отправителем, кратким содержанием, исполнителем, сроком, статусом и индикатором просрочки;
- поиск по номеру, отправителю и содержанию;
- фильтры по периоду, типу, статусу, исполнителю, подразделению, наличию просрочки и планируемому результату;
- сортировка по дате регистрации и сроку;
- пагинация в соответствии с архитектурой проекта;
- сохранение фильтров в URL, если это принято в проекте;
- экспорт отфильтрованного списка, только если в проекте уже есть безопасный механизм экспорта.

### Карточка

Карточка должна содержать логические блоки:

1. регистрационные данные;
2. исходный документ и вложения;
3. резолюция;
4. исполнители и сроки;
5. ход исполнения / история комментариев;
6. результат;
7. связанные приказы и документы;
8. история изменений.

Обязательны понятные ошибки валидации, подтверждение значимых действий и доступность форм с клавиатуры.

### Представления контроля

Добавь готовые фильтры или вкладки:

- Мои документы;
- Требуют рассмотрения;
- В работе;
- Срок истекает;
- Просрочено;
- На проверке контролёра;
- Закрыто.

## 6. Права доступа

Адаптируй права к существующей RBAC/ACL-модели. Минимальные роли процесса:

- **Регистратор** — создание и изменение регистрационных реквизитов до передачи на рассмотрение;
- **Руководитель** — резолюция, назначение исполнителей и срока;
- **Исполнитель** — просмотр порученных записей, обновление хода и результата;
- **Контролёр** — проверка результата, закрытие и возврат в работу;
- **Администратор** — справочники и полный доступ.

Пользователь не должен получать доступ к закрытым или чувствительным документам только по прямому URL. Авторизацию проверять на сервере для чтения, изменения, скачивания вложений и экспорта.

## 7. Правила и валидации

- регистрационный номер уникален;
- дата регистрации не может отсутствовать;
- дата поступления не должна быть позже даты регистрации без явного разрешённого исключения и комментария;
- при назначении исполнителя обязательны срок и резолюция;
- закрыть запись можно только при наличии результата и даты исполнения;
- при передаче по компетенции обязательны получатель и комментарий;
- при отмене обязательна причина;
- продление срока сохраняет прежний срок, новый срок, основание, автора и время изменения;
- все изменения статуса, исполнителя, срока, резолюции и результата попадают в аудит;
- файловые вложения проходят существующие проверки типа, размера, прав и безопасной выдачи;
- даты хранятся и передаются по правилам проекта, а отображаются в локальной временной зоне пользователя.

## 8. Уведомления

Подключи существующий механизм уведомлений, если он есть:

- назначен исполнитель;
- изменён срок;
- приближается срок исполнения;
- срок просрочен;
- запись возвращена в работу;
- результат принят и запись закрыта.

Не внедряй новый внешний канал уведомлений без согласования. Если механизма нет, подготовь доменные события и точки интеграции, а фактическую отправку оставь отдельной задачей.

## 9. Миграции и данные

- добавь обратимые миграции;
- подготовь начальные значения справочников идемпотентно;
- не изменяй существующие данные приказов разрушительным образом;
- для локальной разработки добавь небольшие демонстрационные данные только принятым в проекте способом;
- если есть импорт из текущего Excel-реестра, не смешивай его с основной реализацией: оформи отдельной командой/скриптом с dry-run и отчётом об ошибках.

## 10. API и журналирование

Следуй текущему стилю API. Для списков используй серверные фильтры, сортировку и пагинацию. Исключи массовую загрузку полного реестра в браузер.

Журнал аудита должен позволять понять: кто, когда, какое поле изменил, прежнее и новое значение. Не записывай в обычные технические логи полный текст чувствительных документов, жалоб, персональные данные и содержимое вложений.

## 11. Тесты

Добавь тесты в принятом в проекте объёме:

- генерация уникального регистрационного номера, включая конкурентные запросы;
- переходы статусов и запрещённые переходы;
- вычисление просрочки;
- валидация закрытия, отмены, передачи и продления срока;
- права регистратора, руководителя, исполнителя, контролёра и постороннего пользователя;
- связь входящей записи с одним и несколькими приказами;
- фильтры списка;
- серверная защита карточки и вложений;
- ключевой пользовательский сценарий от регистрации до закрытия.

## 12. Критерии приёмки

Задача считается выполненной, если:

1. входящий документ можно зарегистрировать и он получает уникальный номер;
2. руководитель может вынести резолюцию, назначить исполнителя и срок;
3. исполнитель видит поручение, фиксирует ход и результат;
4. просроченные записи определяются автоматически;
5. контролёр может принять результат и закрыть запись либо вернуть в работу;
6. входящая запись связывается с одним или несколькими приказами без текстового дублирования реквизитов;
7. пользователь видит историю значимых изменений;
8. ограничения доступа работают на сервере;
9. миграции, линтер, типизация и тесты проекта проходят;
10. существующий функционал реестра приказов не сломан.

## 13. Порядок работы Cursor

1. Сначала изучи репозиторий и найди существующие модели сотрудников, подразделений, пользователей, ролей, документов, файлов, приказов, справочников, аудита и уведомлений.
2. До изменения кода кратко опиши найденную архитектуру и предложи план: какие таблицы, связи, маршруты, компоненты, миграции и тесты будут затронуты.
3. Перечисли вопросы, которые действительно блокируют реализацию. Не останавливайся из-за несущественных деталей — используй текущие соглашения проекта.
4. Реализуй задачу небольшими логичными изменениями, сохраняя обратную совместимость.
5. Запусти проверки проекта и исправь вызванные изменениями ошибки.
6. В финальном отчёте укажи изменённые файлы, миграции, реализованные сценарии, результаты тестов, известные ограничения и безопасный порядок развёртывания.

## 14. Что не входит в первую версию

- OCR и автоматическое распознавание вложений;
- автоматическая юридическая классификация жалоб;
- автоматическое решение о дисциплинарном взыскании;
- интеграция с внешней почтой и ЭДО, если её уже нет в проекте;
- квалифицированная электронная подпись;
- сложный BPMN-конструктор;
- массовая миграция исторических документов без отдельного согласованного плана.

## 15. Реализованные этапы backend

### Foundation (`wp_ii_001`, revision `d1e2f3a4b5c6`)

- регистрация, список/карточка, вложения, связи с приказами, RBAC, RESTRICTED-доступ, аудит создания;
- миграция не изменяется; исправления только additive-миграциями.

### Workflow / FSM (`wp_ii_002`, revision `e2f3a4b5c6d7`, parent `d1e2f3a4b5c6`)

**Статусы FSM**

| Код | Тип |
|-----|-----|
| `REGISTERED` | начальный |
| `ASSIGNED` | рабочий |
| `IN_PROGRESS` | рабочий |
| `WAITING_INFORMATION` | рабочий |
| `RESOLVED` | рабочий (результат зафиксирован) |
| `CLOSED` | терминальный (выход через `reopen`) |
| `CANCELLED` | терминальный |
| `TRANSFERRED` | терминальный (внешняя передача) |

**Основная цепочка:** `REGISTERED → ASSIGNED → IN_PROGRESS ↔ WAITING_INFORMATION → RESOLVED → CLOSED`

**Просрочка:** только вычисляемый `is_overdue`; статус `OVERDUE` не используется.

**Optimistic locking:** все workflow-операции принимают `expected_version`; конфликт → `409 VERSION_CONFLICT`.

**Endpoints** (prefix `/api/incoming-information/incoming-documents/{id}/`):

| Операция | Path | Permission (минимум) |
|----------|------|----------------------|
| assign | `POST …/assign` | `INCOMING_INFO_CONTROL` |
| reassign | `POST …/reassign` | `INCOMING_INFO_CONTROL` |
| transfer | `POST …/transfer` | `INCOMING_INFO_CONTROL` |
| start | `POST …/start` | активный PRIMARY + `INCOMING_INFO_EXECUTE` |
| request-information | `POST …/request-information` | активное назначение + execute |
| resume | `POST …/resume` | активное назначение + execute |
| change-deadline | `POST …/change-deadline` | `INCOMING_INFO_CONTROL` |
| resolve | `POST …/resolve` | PRIMARY / контролёр / `INCOMING_INFO_RESOLVE` |
| close | `POST …/close` | контролёр документа / `INCOMING_INFO_CONTROL` |
| reopen | `POST …/reopen` | контролёр документа / `INCOMING_INFO_CONTROL` |
| cancel | `POST …/cancel` | `INCOMING_INFO_REGISTER` (REGISTERED/ASSIGNED) или `INCOMING_INFO_CONTROL` (IN_PROGRESS/WAITING_INFORMATION) |

**Схема (additive):** `row_version`, поля close/cancel/transfer/reopen, `incoming_document_deadline_changes`, `incoming_document_transfers`, исправление CHECK `file_id`, seed статусов `ASSIGNED`, `WAITING_INFORMATION`, `RESOLVED`, расширение audit `OPERATION_*`.

### Review fixes (`wp_ii_003`, revision `f3a4b5c6d7e8`, parent `e2f3a4b5c6d7`)

- колонки `control_decision`, `control_comment` на документе (close/reopen);
- permission `INCOMING_INFO_RESTRICTED_BYPASS` (отдельно от `INCOMING_INFO_CONTROL`);
- ужесточён RESTRICTED-доступ: `org_scope` и `INCOMING_INFO_CONTROL` без участия не дают доступ;
- расширенные тесты external transfer, RESTRICTED, concurrency, rollback, invariants.

### RESTRICTED closure and review bundle (`wp_ii_004`)

**Normative alignment:** [ADR-064 §D4](../adr/ADR-064-incoming-document-party-addressing.md) (amended WP-II-005R7).

**Правило доступа к защищённому содержанию (`access_level = RESTRICTED`)**

Для интерактивного пользователя доступ к **защищённому содержанию** RESTRICTED-документа
(карточка, audit, вложения, связи) разрешён **только** при выполнении хотя бы одного условия:

1. пользователь является **участником документа**;
2. у пользователя есть явный grant `INCOMING_INFO_RESTRICTED_BYPASS`.

**Участники документа**

- регистратор (`created_by_user_id`);
- адресат (`addressee_user_id` или `addressee_employee_id`, связанный с текущим пользователем);
- активный назначенный исполнитель (любая активная запись в `incoming_document_assignments`);
- назначенный контролёр (`controller_user_id`).

**Административное управление ≠ чтение защищённого содержания**

- `INCOMING_INFO_ADMIN` — модульное администрирование и расширенные права на **NORMAL**
  записи в зоне RBAC; **не** даёт автоматического чтения RESTRICTED protected content.
- `INCOMING_INFO_CONTROL`, `INCOMING_INFO_REGISTER`, `INCOMING_INFO_EXECUTE`,
  `INCOMING_INFO_RESOLVE` без участия в документе **не** открывают RESTRICTED content.

**Не дают bypass RESTRICTED сами по себе**

- `is_privileged` (directory env-allowlist, `role_id = 2` / SYSTEM_ADMIN);
- технический / системный администратор;
- `can_admin` / `INCOMING_INFO_ADMIN`;
- каталожная роль директора / заместителя без явного `INCOMING_INFO_RESTRICTED_BYPASS`;
- org-scope (`responsible_org_unit_id` в зоне пользователя).

`INCOMING_INFO_RESTRICTED_BYPASS` выделен отдельным permission (WP-II-003) и **может**
входить в утверждённые ролевые пакеты (например профиль директора или профильного
администратора модуля), но наличие роли без этого grant bypass **не создаёт**.

Общий privileged-bypass ради обратной совместимости **не используется**. Отдельного
системного service principal для модуля «Входящая информация» нет: `is_privileged`
относится к интерактивным пользователям и не обходит RESTRICTED.

**Агрегированная управленческая отчётность (future work, не реализовано в WP-II)**

Сводные показатели (counts, статусные breakdowns, просрочка) без bypass допустимы
**только** если не раскрывают тексты, файлы и иные чувствительные поля отдельных
RESTRICTED-записей. Отдельный reporting API в WP-II backend **не входит** в scope.

**Аудит чтения чужого RESTRICTED (future work, не реализовано в WP-II)**

Чтение RESTRICTED non-participant через bypass **должно** аудироваться (actor, document,
timestamp). В WP-II реализован lifecycle/attachment audit; dedicated bypass-read audit
**отложен**.

**Где применяется правило (реализовано)**

- чтение одного документа и audit;
- список документов — RESTRICTED-записи, недоступные пользователю, **не возвращаются**;
- все workflow-endpoints: `assign`, `reassign`, `transfer`, `start`, `request-information`, `resume`, `change-deadline`, `resolve`, `close`, `reopen`, `cancel`;
- вложения и связи с приказами (через проверку доступа к родительскому документу).

**Реализация:** `access_service.user_is_restricted_participant`, `can_restricted_bypass` (только явный grant), `query_service.list_incoming_documents` (фильтрация RESTRICTED).

**Тесты:** `tests/incoming_information/test_access_control.py`, `tests/incoming_information/test_workflow_restricted_access.py`.

### Final backend review fixes (`wp_ii_005r1`)

PostgreSQL и файловая система не участвуют в одной транзакции. Для вложений используется **компенсирующий файловый протокол** с явными границами crash-consistency: при аварийном падении процесса между шагами возможны кратковременные рассогласования (staging/part, quarantine/trash), которые устраняются синхронной компенсацией в том же запросе или идемпотентной повторной очисткой артефакта.

#### Upload (компенсирующий протокол)

Порядок:

1. потоковая запись в `_staging/{staging_id}.part`;
2. валидация содержимого staging;
3. `promote` staging → permanent (`{document_id}/{file_id}.{ext}`) **до** commit БД;
4. INSERT вложения и audit `ATTACHMENT_ADDED` в одной БД-транзакции;
5. commit БД.

Компенсация:

| Точка отказа | Действие |
|---|---|
| ошибка `promote` | INSERT/audit не выполняются; staging остаётся (или удаляется при повторной ошибке); permanent отсутствует |
| ошибка INSERT или audit | rollback БД; удаление permanent-файла |
| ошибка commit после успешного `promote` | rollback БД; удаление permanent-файла |

Промежуточный `commit()` в service/repository не используется.

#### Delete (quarantine-протокол)

Порядок:

1. атомарный `rename` permanent → `_quarantine/{quarantine_id}.trash`;
2. DELETE строки вложения и audit `ATTACHMENT_REMOVED` в одной БД-транзакции;
3. commit БД;
4. best-effort удаление quarantine-артефакта.

Компенсация:

| Точка отказа | Действие |
|---|---|
| ошибка перемещения в quarantine | DELETE/audit не выполняются; permanent остаётся на месте |
| ошибка DELETE или audit | rollback БД; `restore` файла из quarantine на permanent |
| ошибка финальной очистки quarantine после commit | операция считается успешной (не `500`); permanent недоступен; БД не откатывается; остаётся явный cleanup-артефакт `_quarantine/*.trash`, удаляемый идемпотентно через `cleanup_quarantine_artifact` |

#### Crash-consistency (границы)

- между `promote` и commit при crash процесса теоретически возможен orphan permanent без записи БД — в штатном синхронном пути компенсируется удалением permanent;
- между quarantine-move и commit при crash теоретически возможен файл в quarantine при живой записи БД — в штатном пути восстанавливается при rollback;
- после успешного commit delete и неудачной cleanup quarantine допустим явный `.trash`-артефакт; повторный вызов cleanup безопасен.

#### `responsible_org_unit_id`

При явной передаче в регистрации выполняется `org_unit_exists` до INSERT (как для других reference ID). Несуществующий ID → `422`; документ, стороны, назначения и audit не создаются.

**Тесты:** `test_attachment_transactions.py` (upload/delete failure paths, happy path, quarantine retry), расширение `test_input_validation.py` (`responsible_org_unit_id`).

### Transaction boundary proof (`wp_ii_005r2`)

#### Delete: pre-commit vs post-commit

**Pre-commit** (до успешного `commit` транзакции DELETE/audit):

1. permanent перемещён в `_quarantine/{id}.trash`;
2. выполняются SQL DELETE и audit;
3. при любой ошибке или rollback — `restore` из quarantine в permanent;
4. partial changes в БД не остаются.

**Post-commit** (после успешного `commit`):

1. permanent **никогда** не восстанавливается;
2. `_best_effort_cleanup_quarantine_after_commit()` вызывается вне pre-commit `except`;
3. любое исключение cleanup перехватывается, логируется через `logging`, API не возвращает ложный `500`;
4. подтверждённое удаление БД не отменяется;
5. `.trash` остаётся распознаваемым артефактом; повторная очистка — `cleanup_quarantine_artifact(quarantine_id)` (идемпотентно).

#### Upload: commit boundary

Отказ `Connection.commit()` до фиксации транзакции INSERT/audit компенсируется удалением permanent-файла; записи в БД нет.

#### Failure-point tests

- реальный отказ `Connection.commit` при upload;
- реальный SQL INSERT failure (`Connection.execute` на INSERT);
- реальный SQL DELETE failure через `execute_attachment_deletion`;
- audit failures upload/delete — отдельно;
- post-commit cleanup: `RuntimeError` и `return False` — операция успешна для клиента.

**Regression:** оба pytest-набора на пересозданной `corpsite_test` (drop/create + `alembic upgrade head`).
