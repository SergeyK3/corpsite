# Удаление тестовых записей персонала с двойным подтверждением

| Поле | Значение |
|---|---|
| Статус | **Draft — требуется согласование** |
| Дата | 2026-09-04 |
| Назначение | Требования для владельца продукта, Codex и других агентов |

> Решения для серверной основы WP-TD-002 приняты 2026-09-04. Физическое
> удаление, статусы исполнения и endpoint исполнения в WP-TD-002 не входят.

## 1. Цель

Создать безопасный механизм физического удаления тестовых записей персонала и претендентов из production-системы.

Удаление выполняется только после последовательного участия:

1. системного администратора;
2. руководителя отдела кадров (`HR_HEAD`);
3. системного администратора, выполняющего утверждённое удаление.

Механизм не заменяет увольнение, архивирование и исправление карточек реальных сотрудников.

## 2. Основные ограничения

* Реальный сотрудник не должен физически удаляться через этот механизм.
* Маска используется только для поиска и предварительного выбора записей.
* При создании запроса результат поиска преобразуется в точный неизменяемый список технических ID.
* При исполнении маска повторно не применяется.
* Одобрение относится только к зафиксированному списку записей.
* Любое изменение состава или связанных данных после одобрения блокирует удаление и требует повторного рассмотрения.
* Удаление выполняется одной транзакцией: либо удаляется весь утверждённый набор, либо не удаляется ничего.
* Все действия записываются в неизменяемый аудит.

## 3. Размещение функций

### 3.1. Кабинет системного администратора

Создать отдельную административную панель:

**«Управление тестовыми данными персонала»**

Основные действия:

* **«Создать запрос на удаление»**;
* **«Отменить запрос»** — до исполнения;
* **«Выполнить утверждённое удаление»** — только после одобрения `HR_HEAD`.

На панели отображаются:

* номер запроса;
* инициатор;
* дата создания;
* критерии поиска;
* количество выбранных записей;
* статус;
* сведения об одобрении руководителем отдела кадров;
* результат выполнения.

### 3.2. Кабинет руководителя отдела кадров

Создать раздел или очередь:

**«Согласование удаления тестовых данных»**

Действия руководителя:

* **«Одобрить удаление»**;
* **«Отклонить»**.

Руководитель отдела кадров не выполняет физическое удаление.

## 4. Выбор записей системным администратором

Системный администратор может формировать предварительный список:

* ручным выбором отдельных записей;
* по точным техническим ID;
* по безопасной маске;
* по источнику создания или тестовой загрузке;
* по типу записи: сотрудник или претендент;
* по дате создания;
* по сочетанию разрешённых фильтров.

### 4.1. Маски

Поддерживать простую маску:

* `*` — любое количество символов;
* `?` — один символ.

Не принимать SQL-шаблоны и произвольные регулярные выражения.

Примеры:

* `Debug Applicant*`
* `Demo Intake Applicant*`
* `TEST-*`

Маска должна применяться только к явно перечисленным полям, например ФИО или тестовому идентификатору. Она не должна интерпретироваться как SQL.

### 4.2. Фиксация результата

После поиска система показывает предварительный список.

Перед созданием запроса системный администратор обязан подтвердить точные записи. Затем сервер сохраняет:

* отсортированный список технических ID;
* тип каждой записи;
* критерии поиска и маску;
* количество записей;
* контрольный hash списка;
* fingerprint разрешённых связанных данных;
* дату и время фиксации;
* инициатора;
* причину удаления.

В MVP при создании используется только структурированный `reason_code`. Свободный
комментарий создания не принимается; безопасный необязательный комментарий доступен
только при approve/reject.

Расширение маски после создания запроса не должно добавлять новые записи.

## 5. Предварительная проверка безопасности

Для каждой выбранной записи сервер выполняет проверку связанных данных.

### 5.1. Нормативная relationship policy

| Класс связи | Категория | Допустимость foundation |
|---|---|---|
| Employee, assignment, user/identity, любая legacy `personnel` или logical `contacts.person_id` | `BLOCK` | create/submit/approve/future execution запрещены |
| Официальные кадровые события, приказы, incoming documents, onboarding, personnel-order contour | `BLOCK` | create/submit/approve/future execution запрещены |
| Профильные PPR sections и Telegram | `BLOCK` | create/submit/approve/future execution запрещены |
| `personnel_record_events`, `ppr_command_executions` | `TOMBSTONE_REQUIRED` | create/submit/approve разрешены; future execution запрещён до отдельного tombstone/hash WP |
| Ранний application lifecycle allowlist | `TOMBSTONE_REQUIRED` | create/submit/approve разрешены; future execution запрещён |
| Официальный application lifecycle/resolution | `BLOCK` | create/submit/approve/future execution запрещены |
| `intake_submitted` | `HR_ATTESTATION_REQUIRED` | approve только с явным решением `HR_HEAD`; каждый переход повторно проверяет status |
| `personnel_record_metadata`, все applications, intake links/drafts | `INFORMATIONAL` | входят в canonical fingerprint и сами не блокируют approval |
| Retained security/enrollment/import/order audit и provenance state | `INFORMATIONAL` | сохраняются, входят в canonical fingerprint и повторно проверяются |

Каждая связь имеет server-owned lookup, технические keys, canonical state digest и явные
stage flags. Любой неизвестный или неописанный inbound link обрабатывается fail closed.

Одобрение `HR_HEAD` не должно обходить эти блокировки.

### 5.2. Предварительный просмотр

До отправки на согласование показываются:

* запись;
* её тип;
* основание считать её тестовой;
* найденные связи;
* какие строки предполагается удалить;
* какие данные сохранятся в аудите;
* блокирующие причины.

Записи с блокирующими связями нельзя включить в запрос.

## 6. Согласование руководителем отдела кадров

`HR_HEAD` видит точный зафиксированный список, а не только исходную маску.

Руководителю показываются:

* номер запроса;
* инициатор;
* причина;
* использованная маска и фильтры;
* количество записей;
* список записей;
* кадровый статус;
* результаты проверки связей;
* контрольный hash;
* срок действия запроса.

Для просмотра кадровых данных применяется действующий организационный scope. В контуре
WP-TD ИИН всегда показывается только в маскированном виде; capability полного ИИН отсутствует.

При одобрении сохраняются:

* идентификатор одобрившего пользователя;
* роль;
* дата и время;
* решение;
* комментарий;
* hash утверждённого списка;
* версия запроса.

## 7. Отражение одобрения у системного администратора

После одобрения в кабинете сисадмина должен отображаться отдельный текстовый блок:

**«Удаление одобрено руководителем отдела кадров»**

Также показываются:

* ФИО одобрившего;
* дата и время;
* комментарий;
* количество утверждённых записей;
* контрольный hash или его сокращённое представление;
* срок действия одобрения.

Одобрение нельзя обозначать только цветом.

Кнопка **«Выполнить утверждённое удаление»** активна только при наличии действующего одобрения именно для текущей версии и текущего hash списка.

## 8. Повторная проверка перед удалением

После нажатия **«Выполнить утверждённое удаление»** сервер обязан повторно проверить:

* наличие действующего одобрения `HR_HEAD`;
* совпадение версии запроса;
* совпадение списка ID и hash;
* срок действия одобрения;
* отсутствие новых связанных данных;
* отсутствие новых назначений, приказов, событий и документов;
* наличие разрешения у исполнителя;
* что запрос ещё не был выполнен или отменён.

Если данные изменились:

* удаление не выполняется;
* запрос получает статус **«Требуется повторное согласование»**;
* прежнее одобрение становится недействительным;
* `HR_HEAD` должен рассмотреть обновлённый запрос повторно.

## 9. Окончательное подтверждение

Перед удалением системный администратор должен ввести подтверждающую фразу, содержащую номер запроса или количество записей, например:

`УДАЛИТЬ 12 ЗАПИСЕЙ`

После подтверждения повторный запрос по двойному клику не должен запускать вторую операцию.

## 10. Статусы запроса

* `DRAFT` — список формируется;
* `PENDING_HR_APPROVAL` — направлен руководителю отдела кадров;
* `APPROVED` — одобрен;
* `REJECTED` — отклонён;
* `REAPPROVAL_REQUIRED` — данные изменились;
* `CANCELLED` — отменён инициатором;
* `EXPIRED` — истёк срок;
* `EXECUTING` — выполняется;
* `COMPLETED` — удаление завершено;
* `FAILED` — выполнение завершилось ошибкой.

Переход из `COMPLETED` в другие статусы запрещён.

## 11. Срок действия

Рекомендуемый срок действия одобрения — 24 часа.

После истечения срока требуется повторная проверка и новое одобрение `HR_HEAD`.

## 12. Права доступа

Рекомендуемые отдельные permissions:

* `TEST_PERSONNEL_DELETION_REQUEST` — создание запроса;
* `TEST_PERSONNEL_DELETION_APPROVE` — одобрение `HR_HEAD`;
* `TEST_PERSONNEL_DELETION_EXECUTE` — окончательное выполнение;
* `TEST_PERSONNEL_DELETION_AUDIT_READ` — просмотр аудита.

Назначение по умолчанию:

| Permission | Системный администратор | HR_HEAD |
|---|---:|---:|
| Создать запрос | Да | Нет |
| Одобрить | Нет | Да |
| Выполнить удаление | Да | Нет |
| Просмотреть запрос | Да | Да |
| Просмотреть аудит | По утверждённой политике | По утверждённой политике |

Один пользователь не может одновременно одобрить запрос как `HR_HEAD` и выполнить его как системный администратор.

## 13. Транзакционное удаление

Удаление должно выполняться сервером по явному allowlist таблиц и связей.

Запрещается:

* универсальный динамический `DELETE`;
* каскадное удаление неизвестных связей;
* удаление по повторно вычисленной маске;
* частичное завершение операции;
* игнорирование внешних ключей;
* временное отключение ограничений БД.

При ошибке вся транзакция откатывается.

## 14. Аудит

Аудит должен фиксировать:

* номер запроса;
* точные технические ID или безопасный hash списка;
* инициатора;
* одобрившего `HR_HEAD`;
* исполнителя;
* критерии выбора и маску;
* причину;
* статусы и переходы;
* результаты обеих проверок связей;
* количество удалённых строк по таблицам;
* дату и время;
* request ID;
* результат и безопасный код ошибки.

Аудит не должен хранить лишние копии ИИН, телефонов и других персональных данных.

Аудит удаления не удаляется вместе с тестовыми записями.

## 15. Локальная разработка

Для локальной среды допускается отдельная CLI-команда упрощённой очистки.

Она обязана:

* работать только с БД на loopback;
* проверять, что это не production;
* сначала выполнять dry-run;
* требовать явного подтверждения;
* удалять только точный список ID;
* формировать отчёт об удалённых строках.

Production-процесс через веб-интерфейс всегда требует двойного подтверждения.

## 16. Критерии приёмки

Функция принимается, если подтверждено, что:

1. Маска только формирует предварительный список.
2. После создания запроса фиксируется точный набор ID и hash.
3. Новые совпадения по маске не попадают в существующий запрос.
4. Системный администратор не может одобрить собственный запрос.
5. `HR_HEAD` не может физически выполнить удаление.
6. Без одобрения кнопка исполнения недоступна и backend возвращает отказ.
7. Сисадмин видит, кем и когда одобрено удаление.
8. Изменение связанных данных аннулирует одобрение.
9. Реальные кадровые связи блокируют удаление.
10. Операция атомарна и идемпотентна.
11. Повторное выполнение завершённого запроса ничего не удаляет.
12. Аудит сохраняется после удаления.
13. Права проверяются сервером.
14. Полный сценарий проверен на PostgreSQL.
15. Ни один тест не использует production-БД.

## 17. Последовательность реализации

1. Инвентаризация типов тестовых записей и связанных таблиц.
2. Определение точного allowlist удаляемых данных и блокирующих связей.
3. Проектирование модели запроса, статусов и аудита.
4. Реализация создания запроса и предварительного просмотра для сисадмина.
5. Реализация согласования в кабинете `HR_HEAD`.
6. Реализация отображения одобрения и исполнения у сисадмина.
7. PostgreSQL-интеграционные тесты.
8. Локальная проверка на специально созданных тестовых записях.
9. Отдельное контролируемое production-развёртывание.

## 18. Указание для Codex

До реализации Codex должен:

* изучить существующие модели Person, Employee, претендентов, карточек, назначений, заявлений, приказов, документов и аудита;
* найти действующие административные кабинеты сисадмина и `HR_HEAD`;
* определить существующие permissions и паттерны согласований;
* составить точную матрицу удаляемых и блокирующих связей;
* проверить, имеются ли уже признаки тестовых данных или provenance;
* представить findings и открытые решения.

До утверждения матрицы таблиц и связей нельзя писать endpoint физического удаления, миграцию удаления или кнопку исполнения.

## 19. Уточнения WP-TD-002B

`WP-TD-002B-test-personnel-deletion-foundation-review-closure.md` имеет приоритет над ранними
формулировками WP-TD-001/WP-TD-002. `personnel_record_events`, `ppr_command_executions` и
допустимые ранние lifecycle-события относятся к `TOMBSTONE_REQUIRED`: они разрешают create и
approve manifest, но запрещают future execution до независимого tombstone/hash.
`intake_submitted` относится к `HR_ATTESTATION_REQUIRED`. Legacy personnel/contact,
Employee, назначения, официальные приказы/документы, users/external identities, профильные
PPR и Telegram остаются `BLOCK`.
`personnel_record_metadata`, все заявки Person, intake links/drafts и retained
security/import audit относятся к `INFORMATIONAL` и входят в fingerprint полным безопасным
state digest. Официальный lifecycle/resolution, incoming document contour, onboarding и
personnel-order contour остаются `BLOCK`.

Legacy Employee hard-delete в web process закрыт безусловным HTTP 410 без конфигурационного
escape hatch. Физическое удаление и execution endpoint отсутствуют.

## 20. Принятые решения WP-TD-002

1. Любая строка `employees`, назначение, приказ, официальный документ, пользователь или внешняя идентичность — `BLOCK`.
2. Любая legacy-строка `personnel` и любой логический `contacts.person_id` — `BLOCK`.
3. Профильные PPR-разделы и Telegram bindings/activations — `BLOCK`; `personnel_record_events`, `ppr_command_executions` и ранний lifecycle allowlist — `TOMBSTONE_REQUIRED`, официальный lifecycle — `BLOCK`.
4. `personnel_record_events`, `ppr_command_executions` и допустимый lifecycle-аудит можно будет рассматривать для удаления только в отдельном WP после сохранения независимого hash/tombstone.
5. Существующая запись без защищённого provenance допускается только через `LEGACY_MANIFEST` с точными Person/Application ID.
6. `intake_pending` допускается к согласованию при отсутствии остальных blockers.
7. `intake_submitted` дополнительно требует явной attestации `HR_HEAD`, что запись синтетическая и не является официальным заявлением.
8. Для будущих тестовых записей используется отдельный append-only provenance. Имя, маска, `source=manual` и idempotency key происхождение не доказывают.
9. Permissions назначаются role-grants: `ADMIN` — REQUEST/EXECUTE/AUDIT_READ, `HR_HEAD` — APPROVE/AUDIT_READ. Наличие роли не создаёт bypass серверной permission-проверки.
10. Legacy Employee hard-delete безусловно отвечает HTTP 410 во всех web-средах; конфигурационного или локального escape hatch нет.
11. WP-TD-002 реализует только `DRAFT`, `PENDING_HR_APPROVAL`, `APPROVED`, `REJECTED`, `REAPPROVAL_REQUIRED`, `CANCELLED`, `EXPIRED`. Физическое удаление отсутствует.
