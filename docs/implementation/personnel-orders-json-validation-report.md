# Проверка черновика JSON хранения кадровых приказов

Дата: 2026-09-23. Проверены десять отобранных записей Лист1 книги «Ручное
распознавание журналов.xlsx» и доступные DOCX из «2026 ПРИКАЗ». Полные
JSON-представления с ПДн находятся только в
local-archive/personnel-orders-json-validation/validated-orders.json.

## Метод и границы

Лист1 использован для выбора разнообразных наименований. Текст DOCX проверялся
до назначения action_type. У большинства DOCX нет номера и даты издания,
по которым их можно однозначно связать с конкретной строкой журнала. Поэтому
в JSON номер и дата оставлены null, а журнальная строка указана лишь как
JOURNAL_REFERENCE с пометкой selection only.

Это не означает, что журнал ошибочен или DOCX не относится к типу: только то,
что в данной выборке связь «строка журнала ↔ конкретный блок DOCX» не доказана.
Особенно осторожно следует читать строки с пометкой самого журнала о
неразборчивости или требуемой визуальной проверке.

## Варианты, которые можно и нельзя объединять

| Группа | Вывод |
|---|---|
| Қосымша ақы туралы и Қосымша ақы төлеу туралы | В выборке текст первого варианта подтверждает SUPPLEMENTARY_PAY. Точный текст второго варианта не связан с журналом, поэтому объединять варианты в один тип пока нельзя. |
| Ауыстыру туралы и Тегін және әкесінің атын ауыстыру туралы | Не один тип: первый текст оформляет перевод плюс совмещение, второй — смену фамилии. Сходство слова ауыстыру недостаточно для TRANSFER. |
| Три варианта «… мәліметіне/мәліметтерге өзгеріс енгізу …» | Категория и образование — разные предметы. Категория подтверждённо относится к QUALIFICATION_CATEGORY; образование оставлено без типа. |
| Қоса атқару туралы и Ставканы алып тастау туралы | Разные, но связанные типы: начало и прекращение совмещения. Тексты подтверждают соответственно CONCURRENT_DUTY_START и CONCURRENT_DUTY_END. |

## Что поместилось в текущую структуру

- Общие реквизиты с null для не доказанных номера и даты.
- Несколько actions в одном документе для одного сотрудника: перевод и начало
  совмещения.
- Нулевой либо один сотрудник у пункта; employee_id и person_id оставлены
  null, когда сопоставление не проводилось.
- Каноническое ФИО и только фактически встретившаяся падежная форма.
- Отдельные основания, включая личное заявление и служебную записку, с
  basis_ids у соответствующих действий.
- Отдельные source_files для DOCX и журнала; журнальная ссылка не подменяет
  файл приказа.
- Период отпуска и другие даты действия через effective_period, без
  дублирования дат отпуска в data.

## Поля и факты, которые не помещаются без неявного расширения

| Наблюдение | Причина |
|---|---|
| Смена фамилии и отчества | Нет точного action_type; неверно использовать TRANSFER. |
| Изменение сведений об образовании | Нет точного action_type; в тексте есть уровень образования, специальность и диплом. |
| Диплом как самостоятельное основание | Нет точного document_type: OTHER сохраняет факт, но теряет различимость диплома. |
| Сертификат специалиста для квалификационной категории | MEDICAL_CERTIFICATE слишком узок и не точно передаёт профессиональный/квалификационный сертификат. |
| Удостоверение личности при смене фамилии | В текущем перечне нет типа документа, удостоверяющего личность. |
| Один текст содержит заявление и удостоверение личности | Это два разных основания; их нельзя сворачивать в один объект basis_document. |
| Точное соответствие строки журнала блоку DOCX | Схема имеет source_files, но в исходных DOCX часто отсутствуют номер и дата приказа; журнал должен оставаться отдельной ссылкой до ручного подтверждения. |

## Действительно необходимые изменения схемы

1. Добавить action_type для смены персонального имени (например,
   PERSON_NAME_CHANGE) и для изменения сведений об образовании (например,
   EDUCATION_RECORD_CHANGE). До этого значения должны оставаться null.
2. Добавить document_type как минимум для EDUCATION_DIPLOMA,
   PROFESSIONAL_CERTIFICATE и IDENTITY_DOCUMENT. Не заменять профессиональный
   сертификат типом MEDICAL_CERTIFICATE без явного правила.
3. Явно разрешить несколько объектов в basis_documents для одного действия,
   когда заявление и удостоверение личности либо иные документы упомянуты
   раздельно. Текущий массив и basis_ids это технически допускают; требуется
   только закрепить правило редакционного заполнения.
4. Для source_files закрепить статус связи с приказом: журнал может быть
   только кандидатом/ссылкой выбора, пока номер и дата либо ручная проверка не
   подтвердят соответствие DOCX. Без этого есть риск перенести номер и дату
   из неродственной журнальной строки.

Остальные новые сущности не требуются для этой выборки. Код, БД, API и
миграции не изменялись.
