# Личная карточка сотрудника: self-service контур

Статус: руководящий документ для исследования и проектирования
Этап: до реализации
Цель: заменить вкладку «Образование» в личном кабинете сотрудника вкладкой «Личная карточка» и предоставить каждому сотруднику безопасный доступ к просмотру и заполнению только собственной карточки.

## 1. Основной принцип

Личный кабинет не должен использовать кадровый доступ к реестру персонала. Сотрудник работает через отдельный self-service контур, в котором целевая карточка определяется только сервером:

`authenticated user -> linked employee -> linked person/PPR`

Клиент не передаёт `employee_id` или `person_id` для выбора карточки. Подмена идентификаторов и просмотр чужой карточки должны быть невозможны по контракту API.

## 2. Навигация и назначение вкладки

- В верхней навигации сотрудника вкладку «Образование» заменить на «Личная карточка».
- Вкладка открывает собственную карточку сотрудника, а не список работников.
- Рабочее название маршрута: `/profile/personal-card` или согласованный существующей архитектурой эквивалент.
- Старый маршрут «Образование» исследовать до удаления: при наличии внешних ссылок предусмотреть безопасный redirect.
- Доступ к «Кадровому журналу» остаётся отдельной capability и не связан с доступом к собственной карточке.

## 3. Состояния страницы

1. **Карточка существует** — показать разделы и допустимые действия.
2. **Employee существует, Person/PPR отсутствует** — показать нейтральное состояние «Личная карточка ещё не создана» и контролируемое действие «Начать заполнение».
3. **Нет связи User -> Employee** — отказ с понятным сообщением и без возможности передать ID вручную.
4. **Неоднозначная или повреждённая связь** — контролируемый конфликт, без автоматического выбора записи.
5. **Карточка временно недоступна** — безопасная ошибка без внутренних идентификаторов и технических деталей.

До реализации требуется решить, создаёт ли «Начать заполнение» Person/PPR автоматически либо формирует запрос кадровику. Рекомендуемый вариант: идемпотентный серверный bootstrap только при однозначной активной связи User -> Employee и отсутствии Person; операция обязательно аудируется.

## 4. Модель владения данными

| Раздел | Просмотр сотрудником | Изменение сотрудником | Рекомендуемый режим |
|---|---:|---:|---|
| Фото | Да | Да | Прямое сохранение с валидацией |
| Контакты | Да | Да | Прямое сохранение |
| Общие сведения и идентификация | Да, с действующим маскированием | Ограниченно | Запрос на исправление для ИИН, Ф.И.О., даты рождения и иных идентификационных фактов |
| Образование | Да | Да | Прямое сохранение либо отправка на подтверждение — определить по текущей provenance-модели |
| Обучение и повышение квалификации | Да | Да | Прямое сохранение с документальными реквизитами |
| Категория | Да | Нет | Только HR |
| Трудовая биография до текущей организации | Да | Да | Прямое сохранение или подтверждение HR |
| Работа в текущей организации | Да | Нет | Только из operational assignment |
| Воинский учёт | Да | Ограниченно | Запрос на подтверждение HR |
| Родственники | Да | Да | Прямое сохранение, защита персональных данных третьих лиц |
| Иностранные языки | Да | Да | Прямое сохранение |
| Примечание, инвалидность, пенсионный статус | Да, по действующей sensitive policy | Ограниченно | Отдельное решение по чувствительным данным |
| Кадровые приказы | Да, только относящиеся к сотруднику | Нет | Read-only |
| Кадровые обращения | Да, только собственные | Создание обращения | Отдельный workflow |
| Адаптация | Если относится к сотруднику | По текущим правилам | Не смешивать с редактированием PPR |
| История изменений | Да, собственная | Нет | Read-only audit trail |

Окончательная матрица должна быть подтверждена после исследования действующих canonical-моделей, provenance и sensitive-field policy.

## 5. UX страницы

### Верхний блок

- фото;
- Ф.И.О.;
- подразделение и должность из действующего назначения;
- статус заполнения карточки;
- «Скачать PDF» собственной карточки;
- при необходимости — статус проверки изменений кадровиком.

### Навигация внутри карточки

- использовать действующий порядок разделов личной карточки;
- разделы открываются якорями или компактными вкладками;
- показывать индикаторы: «Заполнено», «Не заполнено», «На проверке», «Требует уточнения»;
- не создавать вложенную вертикальную прокрутку;
- корректно работать на узком экране.

### Редактирование

- кнопка «Редактировать» на уровне разрешённого раздела;
- явные «Сохранить» и «Отмена»;
- предупреждение при уходе с несохранёнными изменениями;
- dropdown для canonical enum-полей и «Другое» только там, где это допускает схема;
- серверные ошибки показывать рядом с полем;
- поля HR-владения визуально обозначать как read-only с пояснением, как запросить исправление.

## 6. API и безопасность

Рекомендуемый отдельный namespace:

- `GET /api/ppr/me` — собственная composite-карточка;
- `POST /api/ppr/me/bootstrap` — контролируемое создание/связывание карточки, если принято это решение;
- `GET/PUT /api/ppr/me/contacts`;
- аналогичные узкие section endpoints для разрешённых разделов;
- `POST /api/ppr/me/correction-requests` — запрос исправления HR-владельческих полей;
- `GET /api/ppr/me/history`;
- отдельный защищённый маршрут собственного PDF.

Обязательные правила:

- пользователь аутентифицирован и активен;
- Employee определяется только из серверной связи пользователя;
- Person определяется только сервером;
- ID из URL, query и body не могут выбрать другую карточку;
- отсутствие общей `personnel_visibility` не препятствует чтению собственной карточки;
- self-service право не открывает `/directory/employees`, person-scoped HR API или чужой PDF;
- optimistic locking через `updated_at`/CAS;
- `command_id` и идемпотентный replay для команд;
- audit содержит actor user, employee/person, section, server-side before/after и источник `EMPLOYEE_SELF_SERVICE`;
- соседние ключи composite JSON, provenance и sensitive facts не должны затираться узким обновлением;
- rate limiting и ограничения файлов для фото/документов;
- ошибки не раскрывают существование чужих Employee/Person.

## 7. Capability-модель

Предпочтительно identity-based self access для каждого активного пользователя, связанного с Employee, а не массовая выдача общей personnel visibility.

Исследовать два варианта:

1. self-read/self-edit как встроенное право любого корректно связанного сотрудника;
2. отдельные capabilities `PERSONAL_CARD_SELF_READ` и `PERSONAL_CARD_SELF_EDIT`, назначаемые базовой роли сотрудника.

В обоих вариантах scope всегда `SELF`; организационный scope здесь не используется.

## 8. Workflow подтверждения

Для HR-владельческих и чувствительных полей сотрудник не изменяет canonical значение напрямую:

1. создаёт correction request;
2. видит новое значение со статусом «На проверке» отдельно от действующего canonical значения;
3. HR принимает или отклоняет запрос;
4. применение выполняется серверной командой с аудитом;
5. сотрудник видит результат и комментарий.

Прямо редактируемые разделы должны сохраняться через узкие section-команды и также попадать в audit trail.

## 9. PDF

- PDF строится из текущей canonical self-card projection;
- использует существующий Person-rooted PDF renderer и общий CSS там, где это безопасно;
- employee/person идентификаторы определяются сервером;
- «Работа в текущей организации» берётся только из operational assignment;
- режим PDF не даёт дополнительных прав и отражает ту же политику маскирования, что экран.

## 10. Исследование перед проектированием

Codex должен установить:

- фактическую реализацию вкладки «Образование» и последствия её замены;
- существующий User -> Employee -> Person/PPR resolver;
- поведение для Employee без Person на примере employee 228;
- какие section editors и Person-scoped endpoints можно безопасно переиспользовать;
- какие поля уже имеют narrow write-path, CAS, audit и provenance;
- какие данные считаются HR-owned и sensitive;
- как устроены собственные кадровые приказы, обращения и история;
- может ли действующий PDF-контур получить self projection без person ID от клиента;
- существующие feature flags, permissions и базовая роль сотрудника;
- ограничения миграций и совместимость с текущими ветками `per001/per002` и несвязанным Data Exchange.

## 11. Минимальный первый релиз

Рекомендуемый MVP:

1. вкладка «Личная карточка» вместо «Образование»;
2. безопасный `GET /api/ppr/me`;
3. корректное пустое состояние для Employee без Person;
4. просмотр собственной карточки;
5. редактирование контактов, образования и иностранных языков;
6. read-only текущего назначения и HR-полей;
7. собственный PDF;
8. CAS, audit, unsaved changes и адресные тесты.

Bootstrap Person и workflow кадрового подтверждения допускается вынести в отдельный этап, если исследование выявит риск нарушения canonical/provenance модели.

## 12. Критерии приёмки проектирования

- сотрудник не может выбрать или обнаружить чужую карточку;
- доступ работает без personnel visibility;
- Employee без Person получает предусмотренное состояние, а не 404 без объяснения;
- разделы разделены на employee-owned и HR-owned;
- текущая организация не вводится вручную;
- узкие обновления не повреждают соседние данные;
- все изменения аудируются;
- PDF и экран используют одинаковую self projection и маскирование;
- существующий HR-контур и доступ `PERSONNEL_EVENTS_READ` не расширяются;
- документ исследования содержит карту файлов, API, моделей, рисков, решений и поэтапный план;
- до отдельного разрешения реализация, миграции, commit, push и deploy не выполняются.
